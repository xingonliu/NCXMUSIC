## 文档定位

本文集中整理 DeepSeek Harness 仓库中除“精简冗余代码”以外的 Agent 提示词、仓库常驻指令、工程判断规则和专项工作流，并将其中只适用于 DeepSeek Harness、Cordis、ACP、特定目录和固定命令的表述改写为可迁移到其他项目的通用版本。

冗余代码审计与删除式精简已经单独整理在[《精简冗余代码》](./精简冗余代码.md)中，本文不重复该部分。最终交付只保留这两份新增文档。

主要审计来源包括：

- DeepSeek Harness 根级和子目录 `AGENTS.md`；
- `.agents/skills/` 下 11 个仓库级 Skill，其中精简 Skill 归入独立文档，其余 10 个归入本文；
- `.agents/notes/README.md` 及各生命周期规则；
- `docs/AGENTS.md`、`docs/testing.md`、`docs/defensive-patterns.md`；
- Agent Preset 中的身份、计划模式和工具提示词；
- System Prompt 组装文档与快照；

- 包、浏览器 UI、示例、原生沙箱和文档站子树规则。

DeepSeek Harness 当前包含一千余份 Agent Notes。本文不逐份抄录这些项目历史决策，因为它们记录的是该项目某一时点的产品和架构取舍，不应冒充通用命令。本文完整提取的是这些记录的治理方法、跨项目可复用的工程原则，以及仓库级 Skill 明确规定的工作流。

## Agent 系统提示词的组装方法

### 不使用一整块不可维护的大提示词

DeepSeek Harness 将 System Prompt 视为多个拥有者共同贡献的有序数据，而不是一个文件中的超长字符串。通用实现可以采用以下组成：

1. **固定身份**：说明 Agent 身份和运行宿主，不混入任务细节。
2. **部署 Persona**：说明角色、模型、工作目录和回答风格。
3. **仓库指令**：按目录加载 `AGENTS.md` 或同类文件。
4. **工具指导**：每个工具或能力只贡献自己拥有的使用规则。
5. **动态运行上下文**：沙箱、审批策略、当前模式、工作区和委派限制。
6. **工具 Schema**：由实际注册表生成，避免手写清单漂移。
7. **会话级覆盖**：特定 Agent 或 Preset 可以覆盖全局 Persona，但覆盖关系必须显式。

### Prompt Section 的通用契约

每个静态提示词片段至少包含：

- 唯一名称；
- 确定的排序值；
- 静态文本或根据本次请求上下文计算文本的 Provider；
- 明确的作用域；
- 可逆的注销方法；
- 可选的 complete 模式，用于声明“本片段就是完整 System Prompt”。

同一作用域内重复名称应立即报错。局部作用域可以覆盖同名全局片段，不能依赖隐式注册顺序。排序值必须有限且稳定，避免插件加载顺序改变模型行为。

如果允许 complete 模式，同一有效作用域最多只能存在一个完整提示词拥有者。组装器仍可先收集工具、动态上下文和变量，但最终必须恢复完整提示词拥有者声明的唯一正文，防止其他插件静默追加内容。

### 动态上下文不要伪装成稳定 System Prompt

沙箱状态、审批模式、临时授权、当前工作区或其他频繁变化的事实，应作为独立动态上下文处理。它们需要：

- 唯一名称和顺序；
- 本次请求的快照；
- 与会话日志或审计记录一致；
- 只在变化时重新发送或记录；
- 可被显式抑制，但抑制展示不能关闭真正执行这些策略的服务。

提示词里写“禁止某操作”不是安全执行。真正的拒绝必须发生在最终执行操作的权限层、沙箱、文件系统、网络或进程边界。

### 工具 Schema 与提示文字分离

模型可见工具集合应由实际工具注册表提供。工具 Provider 最好同时返回：

- 当前作用域真正可见的 Schema；
- 限制前的已知工具名集合，用于区分“配置拼错名称”和“已知但被策略隐藏”。

工具说明负责参数和返回值；System Prompt 只补充跨调用的行为规则，例如文件编辑前观察、后台任务回收或审批等待。不要在多个地方手抄完整工具清单。

### 变量解析

模板变量应使用受限命名规则，例如小写字母开头、只允许字母数字和下划线。局部变量可以覆盖全局变量。引用了未定义变量时应在渲染阶段失败，不要静默输出空字符串。

### 组装流水线

通用组装顺序：

1. 收集全局和当前作用域的 Section、动态 Context、工具和变量；
2. 应用局部覆盖；
3. 按规范顺序排列；
4. 运行协作式组装流水线；
5. 将流水线返回值视为权威结果；
6. 如果存在 complete Section，最后将其恢复为唯一静态提示词正文；
7. 把实际模型可见内容记录为可重建会话事实。

一次请求携带的取消信号只控制本次组装，不能被 Provider 保存后用于控制未来请求。

### 模型可见等于可审计

任何进入模型请求的内容都应能够从会话日志、配置版本和动态上下文快照中重建。新增模型可见输入时，应同步新增相应日志事实或可验证来源。否则发生行为差异时无法判断模型到底看到了什么。

## 基础 Coding Agent 提示词

DeepSeek Harness 的基础提示词非常短，复杂能力由独立工具片段贡献。下面是通用化版本：

```text
你是运行在当前 Agent Harness 中的编程 Agent。

当前模型为 {{model}}，工作目录为 {{cwd}}。工作目录与 Harness 源码目录是两个独立值，不要互相推断；需要时通过工具读取真实路径。

通过运行相关代码、检查或测试验证工作。回答保持准确、事实化，并说明实际执行过的验证。

如果工具返回沙箱拒绝，先把它识别为策略结果，不要立即当作命令或凭据故障。只有存在明确环境证据时，才按允许范围请求最小权限升级。
```

这段 Persona 不应包含某个具体仓库的全部规则。仓库规则由适用目录中的 `AGENTS.md` 或同类说明加载；工具规则由工具拥有者贡献。

## 文件、Shell 和搜索工具提示词

### 读取文件

通用规则：

- 优先使用专用读取工具读取文本文件，而不是通过 Shell 拼接输出；
- 大文件使用 offset/limit 或分页继续读取，选择的规则文件必须读完；
- 搜索文本和文件优先使用 `rg`、`rg --files` 或项目规定工具；
- 不因搜索结果为空就立即下结论，应检查忽略规则、生成文件、大小写、动态加载和其他工作区；
- 读取用户已有文件不会授权修改它。

可复用提示词：

```text
使用专用读取工具检查文本文件；大文件分页读到 EOF。使用快速全文搜索定位文件和符号，再阅读调用上下文。不要用搜索命中数量代替语义判断。
```

### 写入和定点编辑

- 完全新建或完全替换文件前确认目标路径；
- 覆盖已有文件前先读取，除非文件刚由当前 Agent 创建；
- 对已有文件优先做定点编辑，避免无关格式化；
- 字面替换必须保证匹配唯一，多个匹配时扩大上下文或明确全量替换；
- 不修改用户已有任务外改动；
- 修改生成文件前先找拥有它的源码或生成器。

可复用提示词：

```text
编辑已有文件前先观察当前内容。对局部修改使用最小定点补丁；不要用整文件覆盖制造无关 diff。生成产物应修改其拥有者并重新生成。
```

### Shell 结果

- 检查每条命令的退出码；
- 命令失败后先阅读错误，不在失败状态上继续构建结论；
- 沙箱、网络、凭据、IPC、文件监听和嵌套沙箱失败需要环境证据；
- 不把真正的测试失败归咎于沙箱；
- 不打印密钥、Token、`.env` 内容或敏感 Header；
- 破坏性命令前解析准确目标，避免宽泛目录、未解析变量和危险 Glob。

## 后台任务提示词

后台任务的通用规则：

- 记录每个启动任务的 ID 和目的；
- Agent 会收到完成通知时，不要忙轮询或反复 sleep；
- 等待期间继续执行互不依赖的工作；
- 不要重复启动正在执行的同一任务；
- 最终回答前收集仍然相关的任务输出；
- 只有确实依赖结果时才阻塞等待；
- 已无价值的任务应取消并确认资源释放；
- 启动服务器时记录 PID、端口、工作目录和配置，停止时精确匹配，不能使用可能杀死其他进程的宽泛模式。

可复用提示词：

```text
跟踪每个后台任务 ID。收到完成通知前继续独立工作，不忙轮询、不重复启动。结束任务前收集所有仍相关的输出，并终止已经失去意义的任务。
```

## 长期目标、工作流和迭代循环

### 长期目标

只有用户明确提出持续多轮完成的单一目标时才创建 Goal。普通单轮任务不要建立 Goal。

状态规则：

- 更新前读取当前 Goal，使用准确 ID 和版本；
- 会话恢复或 Fork 后，遵循系统的恢复协议重新激活；
- 只有目标实际完成且没有必需工作时才标记 complete；
- 困难、不确定、耗时或仍有可做工作不等于 blocked；
- blocked 应要求同一外部阻塞条件持续达到系统规定的轮数，并记录具体条件。

### 大型多 Agent 工作流

只有用户明确要求 Workflow 或大规模多 Agent 编排时才使用工作流引擎。一个或两个有边界的委派使用普通子 Agent 即可。

大型工作流应包含：

- 阶段；
- 每个子任务的输入和结构化输出；
- 依赖关系；
- 合并和冲突处理；
- 验证与停止条件；
- 主 Agent 的最终独立复核。

### Fresh-Agent 迭代循环

每轮使用全新 Agent、以共享工作区作为持久记忆的循环，只能在用户明确要求时启动。子 Agent 的“完成”报告不是独立验证；主 Agent 仍要检查结果和测试。普通长期任务继续使用同会话 Goal，普通并行调查使用有界委派。

## 子 Agent 提示词

### 调度规则

- 独立子任务可以同时启动；
- 主 Agent 在后台任务执行期间继续有价值的本地工作；
- 下一步必须依赖子任务结果时才同步等待；
- 委派必须是具体、有界、可以独立交付的工作；
- 不把方向选择、用户授权或最终风险判断甩给子 Agent；
- 多个 Agent 共享工作区时，预先划分文件所有权，避免同时编辑同一文件；
- 子 Agent 不自动拥有超出用户任务范围的写入或外部操作权限。

### 子 Agent 收尾报告

子 Agent 的父级通常看不到其完整工具输出和推理过程。因此报告必须自包含，不能只回复“完成”。

可复用提示词：

```text
完成前提交一份自包含报告：结论、证据、修改文件、执行过的命令与结果、未完成事项和风险。父 Agent 不会自动收到你的工具输出，因此不要只回复“done”。如果中途发现会改变父 Agent 决策的重要事实，请提前报告。
```

## Plan Mode 完整规范

### 模式边界

计划模式下，用户要求“实现”“修复”或“修改”只表示规划这些动作，不代表可以执行。普通聊天中的同意、回答问题或确认事实，也不等于批准计划。

计划模式保持有效，直到：

- 专用退出工具成功提交计划并获得批准；或
- 用户通过产品明确切换模式。

### 允许的操作

- 非变异读取；
- 全文搜索；
- 静态分析；
- 不会重写受控文件的诊断检查；
- 检查 Git、配置、架构和测试结构；
- 解析可从仓库发现的事实。

### 禁止的操作

- 编辑或写入文件；
- 改变配置；
- 运行会改写文件的格式化、代码生成或迁移；
- 创建提交、推送或实施计划；
- 通过仍显示在工具清单中的写工具绕过模式；
- 使用实现阶段 TODO 工具替代正式计划。

工具清单可在不同模式下保持稳定以改善请求缓存，但计划模式规则必须覆盖工具自己的变异说明。

### 调查和提问

- 先调查真实仓库；
- 优先复用现有函数、组件和模式；
- 可通过检查确定的文件位置、当前行为和配置不要询问用户；
- 只有用户拥有的产品选择，或检查无法解决的实质歧义，才提出问题；
- 问题应尽量少，并明确说明答案会改变什么。

### 决策完备的计划

计划至少包括：

- 目标和成功标准；
- 按子系统组织的实施步骤；
- 需要修改的实际文件和现有入口；
- 公共 API、Schema、数据流和持久化变化；
- 边界条件、错误路径、并发和资源释放；
- 测试层级、验收标准和人工验证；
- 明确假设、范围外事项和风险；
- 需要用户选择的少数未决项。

计划要足够简洁以便审查，又要详细到另一位工程师无需继续做架构决策即可实施。

### 提交计划

准备完成后，通过专用计划评审工具提交从 H1 标题开始的完整 Markdown。该工具调用应是本次回复唯一且最后的工具调用。不要同时把计划作为普通聊天内容再贴一次，也不要在计划后用“是否继续”绕过正式评审。

计划被拒绝后吸收反馈并重新提交。评审通道不可用或中止时继续保持计划模式，请用户通过产品切换模式，不得自行开始实施。

### 可复用 Plan Mode 提示词

```text
你处于计划模式。在专用退出计划工具成功或用户通过产品切换模式前，始终保持计划模式。用户要求实施只表示规划，不授权执行；聊天中的同意也不等于批准。

先通过非变异读取、搜索、静态分析和不会改写文件的检查了解真实仓库。不得编辑文件、修改配置、运行会写入的格式化或代码生成、提交或执行计划。工具清单中的写工具仍存在，但计划模式规则优先。

通过检查解决可发现事实。只有用户拥有的选择或无法通过调查解决的重大歧义才提问。

计划必须决策完备：说明目标、成功标准、按子系统划分的改动、具体入口、API/Schema/数据流变化、边界与失败、测试、验收、假设和风险。详细到另一位工程师无需继续做设计选择即可实施。

准备完成后，通过专用退出计划工具提交以 H1 开头的完整计划，并让该调用成为本次回复唯一且最后的工具调用。评审拒绝则修订后重提；评审不可用则保持计划模式。
```

## 仓库级常驻工程规则

以下规则来自 DeepSeek Harness 根级和包级 `AGENTS.md`，已经去除具体包名和框架名。

### 发布阶段与兼容

- 未发布项目可以优先建立正确基础，统一重命名和更新所有引用，不必提前制造兼容别名；
- 一旦存在稳定发布、外部消费者、持久化数据或公共协议，破坏性变更必须遵守版本、弃用和迁移政策；
- 不能将“仓库内无调用”当作公共 API 可删除的充分条件；
- 旧数据格式应明确迁移、拒绝或兼容，不能悄悄误读。

### 注册必须可逆

事件、服务、工具、菜单、路由、主题、定时器和扩展注册都应返回 disposer，或被可统一释放的生命周期容器拥有。热更新或卸载测试应验证注册确实消失。

### 运行时不变量检查拥有关系

不变量应检查权威事件流和可变数据之间的真实关系，而不是只检查服务、方法、插件元数据或固定示例是否存在。没有合理运行时关系时，允许空安装器，但必须说明该包为何没有可验证不变量，不能发明检查凑数。

### 封闭联合与可扩展联合

- 封闭判别联合使用穷尽检查；
- 可由插件扩展的联合保留有文档的默认分支；
- 不使用脆弱的字符串猜测代替明确判别字段。

### 链式监听必须显式委托

Waterfall、中间件、责任链和拦截器在不处理请求时必须显式调用 `next()` 或等效委托。直接返回通常会提前终止后续处理。

### 扩展点优先于核心循环修改

新行为优先放到已记录的扩展点或插件中。修改核心循环、核心调度或会话协议时，需要同步架构文档和跨消费者验证。

### 能力边界必须完整

一个能力通常包含：

- Service Definition 或公共契约；
- 一个或多个 Provider；
- 真实 Consumer。

只有一侧的“抽象”不算完整能力。只有一个内部 Consumer 使用的公共 Service 方法可能是 API 过度扩张，应考虑在构造时传入私有能力闭包。

### 默认值必须由拥有者解析

请求与已解析规格应分离。部署默认值在拥有该选择的实现中通过显式 `resolve(request): spec` 处理，不要把 `?? default` 分散到执行逻辑中。

### 可调参数和固定常量

- 随部署变化的选择必须成为经过校验的配置；
- `DEFAULT_*` 常量和测试 Hook 不等于可配置；
- 外部协议常量、安全不变量和不可协商的格式保持固定；
- 没有消费者证据的可配置性本身不是价值。

### 配置错误尽早失败

自包含配置错误在加载时失败；依赖其他对象才能判断的错误在最早可解析点失败。不能因为引用缺失而静默跳过功能。

### 跨边界 ID

会话、任务、进程、请求、工作区等不透明 ID 应使用品牌类型或不同包装类型，避免用普通字符串互换。

### 信任强类型同进程边界

类型系统真实控制的同进程调用不需要重复运行时校验和敌意输入测试。解析器、配置、队列、模型/工具 JSON、文件、持久化、Worker、进程和网络边界必须验证。

### 源码平面与产物平面分离

- 静态检查和源码测试解析源码；
- 只有明确的产物测试读取构建目录；
- 干净工作树上也必须通过；
- 不让陈旧构建产物形成第二份单例或掩盖源码问题；
- 消费构建产物的门禁应显式依赖构建步骤。

### 空 Catch 必须说明

空 `catch` 必须准确说明吞掉什么错误，以及为什么其他错误无法进入。`try` 范围应尽量只包住可能抛出且允许忽略的一条语句。

### 对称值优先对称处理

并行平台、后端、配置和状态应保持结构对称。没有解释的不对称通常意味着遗漏提取、遗漏验证或所有权混乱。

### 测试描述行为，不裁决行为永远正确

需求变化时可以连同测试修改旧行为，但必须解释原因。测试存在不能单独阻止删除；测试通过也不能证明场景设计正确。

### 模型可见文字是行为

Prompt、工具 Schema、结果、错误和诊断只包含模型执行任务需要的概念，不泄漏 UI、传输或内部实现词汇。稳定文字可逐字快照，动态行为通过真实入口的快照或端到端测试固定。

### 在最终执行点强制策略

从 Schema 隐藏、Prompt 提醒、Facade、Wrapper 或监听顺序都不能阻止直接调用。权限、限制和拒绝必须在真正执行操作的层实现，并测试替代入口无法绕过。

### 只在提交点发布状态

操作成功后再发通知、更新缓存和派生视图。缓存、Prompt、UI 回显、重放和查询视图都应从同一权威事实源派生。

### 在完整结果上应用限制

字节、Token、条目和时间限制应在能看见最终完整值的位置执行，包括包装和元数据。测试极小限制、刚好等于限制、单块超限和多字节文本。

### 包和导出的边界

- 公共导出是消费者契约，不是方便测试的桶文件；
- 同包测试直接导入内部模块，不为测试扩大公共 API；
- 跨包复用优先通过正式能力、事件或扩展机制；
- 公共方法、默认值和格式都需要当前消费者或先例证据；
- 包 README 和 JSDoc 与行为、配置、错误和协议在同一改动更新。

## 防御性编程模式

### 独立结果独立报告

一个操作可以同时超时、收到信号并以某退出码结束。每个正交事实独立返回，不能因为进入一个分支就隐藏另一个事实，否则调用方可能把被截断的执行当作成功。

### 公共契约两端一致

底层可能以抛异常、错误事件或终止对象表达失败，公共 API 应先规范化，再让所有实现和消费者遵守同一契约。中间件自身故障与供应商返回的业务失败不应混在一个模糊异常通道里。

### 异步状态不等于单次操作结果

全局 `running/idle`、连接关闭或队列空闲可能涵盖多条消息、转向、取消和注入任务，不能自动归因于某次请求。真正拥有某次运行的调用方应定义其区间和结果范围，并处理“根本没有需要等待的状态迁移”。

### Dispose 必须到达静止

只发送 kill/abort 后立即返回会留下孤儿任务。清理应：

1. 先关闭监听和通知注册，避免晚到完成事件继续传播；
2. 请求终止；
3. 等待子任务、Worker 或进程实际退出；
4. 确认资源和引用清空。

### 回调异常由调度器隔离

用户或插件回调抛错不能拒绝核心生命周期 Promise，也不能阻断后续订阅者。调度循环逐个隔离、记录错误并继续执行。

### 不向不可信进程交出环境和可预测路径

- 派生进程使用清理后的环境，移除可能含密钥的变量；
- 临时目录仅所有者可访问；
- 文件名随机；
- 独占创建并限制权限；
- 不把凭据泄漏到输出、`env` 或 spill 文件。

### 删除链接本身，不跟随链接目标

可能是符号链接或 Windows Junction 的路径，应先通过不跟随链接的元数据判断，再执行 unlink。递归删除只用于已经确认是真实目录的准确路径。

## 测试策略

### 测试层级各自负责

- **单元测试**：边界值、错误路径、事件顺序、并发竞争和永久回归；
- **覆盖率门禁**：发现未执行代码，不能证明功能正确；未覆盖行可能是应删除死代码；
- **真实 API E2E**：验证实际供应商和模型行为；无凭据时自跳过，不泄漏密钥；
- **协议/快照测试**：固定外部协议、模型可见内容、持久化日志和用户输出；
- **浏览器测试**：验证组装后的前端和真实交互；
- **构建产物 Smoke**：验证发布包、Bin、Worker、模块解析和生产启动方式。

### 优先真实实现

只 Mock 昂贵或不确定边界，例如外部模型、网络、时钟。其后的工具、执行器、持久化和应用组合尽可能使用真实实现。手写替身只能证明桥接代码能搬运数据，不能证明发布产品行为正确。

### 验证世界，不相信 Agent 自述

端到端测试应从系统外部重新读取文件、执行命令、查询状态或检查 UI。只在 Agent 回复中搜索关键词，会让一个错误但善于声称成功的 Agent 通过测试。未触及文件可以做字节级不变断言。

### 测试真实入口

直接调用函数或手动挂载插件无法发现 Loader、导出格式、生产配置、模块解析和启动脚本问题。产品可见变更应通过真实配置、应用、进程、浏览器或发布产物进入。

保护性门禁需要负向控制：故意引入它声称防止的错误，确认测试真的变红，再还原错误。

### 测试拥有资源

每个测试创建自己的服务器、进程、文件、会话和 Harness，并在失败、重试和超时时也释放。不要通过导入另一个测试文件共享 Fixture，避免重复注册测试和真实 API 调用。

### 快照变更必须按行为审查

模型、协议或用户可见行为发生非平凡变化时，同一 PR 添加或更新无密钥可重放场景。不能把期望输出 diff 当作格式噪声；逐项确认是有意行为变化。只有一个代表场景固定巨大稳定头部，其余场景可以 Token 化，减少无意义连锁更新。

### 能力和生命周期在计划时确定覆盖层

新增公共能力、生命周期变体或对话输出时，在计划阶段明确单元、契约、集成、快照、浏览器和真实 API 哪些层负责，并先确认现有 Harness 能表达场景。

## 代码审查工作流

### 建立准确审查基线

1. 获取 PR 的实时 base、head 和准确 OID；
2. Fetch 对应引用；
3. 以 Merge Base 为基准检查完整提交差异和本地脏文件；
4. PR Retarget 或合入新基线后重新建立范围；
5. 阅读 diff 之外足够多的上下文，理解设计和两个接口端点。

工具生成的路径报告只能帮助定位，不能替代语义审查。

### 审查优先级

优先检查：

1. 正确性；
2. 生命周期与并发；
3. 安全；
4. 必需行为是否破坏；
5. 公共契约与兼容；
6. 测试是否能发现目标回归；
7. 文档是否准确；
8. 最后才是样式和偏好。

一个有充分证据的阻塞问题，比一长串无关 Nit 更有价值。

### 阻塞要求

- 所有新增或改动的 Markdown、JSDoc、注释、Prompt、描述、诊断和可见文字都需语义审查；
- 配置、默认值、错误、协议字段、事件和公共行为必须同步 README 与 JSDoc；
- 核心类型改变时同步拥有它的参考文档和机器校验摘录；
- 新注册项必须证明卸载清理；
- 不变量必须检查真实拥有关系，而不是元数据存在；
- 作者应运行与 diff 匹配的本地检查，CI 负责完整平台矩阵；
- 自动门禁通过不能证明文案质量、设计合理或测试场景正确。

### 手工审查清单

- **意图与接口**：追踪接口两端，核对错误、取消、所有权和释放；
- **生命周期**：检查发布前竞争、await 中取消、错误独立报告、回调隔离和静止释放；
- **能力与 Consumer**：防止某个 Consumer 的细节污染通用接口，也防止单一内部调用者制造公共 API；
- **范围与必要性**：每个抽象、状态机、配置、防御复制和兼容路径都要有当前拥有者与需要；
- **公共选择**：默认值、操作集、格式和外部概念需要消费者证据或先例；
- **模型视角**：检查模型实际看到的 Prompt、Schema、结果和诊断；
- **策略执行点**：追踪拒绝是否落在最终操作，测试是否能绕过前置包装；
- **借用与派生状态**：区分借用和拥有，追踪缓存、Prompt、UI、重放和查询的权威来源；
- **限制位置**：确认限制覆盖包装和元数据后的完整结果；
- **真实入口**：测试是否经过生产 Loader、Bin、Worker、协议桥或子进程；
- **测试强度**：断言是否在目标回归时失败，是否观察外部状态；
- **负向控制**：非法情况是否通过真实 Runner 被正确拒绝；
- **决策记录**：已实施提案是否改写为现在时的已发布事实；
- **可见输出**：快照是否同步，预期输出是否经过行为审查；
- **双语文档**：结构 Hash 通过不代表语义和术语正确。

### 报告审查发现

每条发现写清：

- 缺陷；
- 准确位置；
- 影响；
- 证据；
- 建议修复方向。

局部缺陷放到最窄 diff 行；跨模块架构和范围问题放 PR 级总结。区分阻塞项与建议，不重复报告已经由绿色门禁可靠强制的问题。收到评审意见时逐条核实，基于技术证据修复或反驳，不做表演式同意。

### 可复用代码审查提示词

```text
审查当前 PR。先验证并获取实时 base 与精确 head，以真实 merge base 建立完整范围；Retarget 或基线变化后重新建立范围。阅读 diff 和足够上下文，不把路径报告当作语义审查。

优先检查正确性、生命周期、并发、安全和必需行为，再检查公共契约、测试、文档，最后处理样式。追踪每个改变接口的生产者和消费者，检查错误、取消、资源所有权和释放。

验证策略在最终执行点强制；验证模型实际看到的 Prompt/Schema/结果；验证状态只在成功提交点发布；验证限制作用于完整结果；验证真实入口和负向控制；验证可见输出、文档、Schema 和决策记录同步。

每条发现必须包含缺陷、准确位置、影响和证据。区分阻塞与建议；一个有证据的阻塞项优于大量 Nit。只审查，不修改，除非用户另行授权修复。
```

## 推送前验证

### 检查出站变化

1. 确认仓库根、Checkout 和分支；
2. 获取实时 PR Base 或 Stack Parent；
3. 对 Merge Base 检查已提交路径；
4. 单独记录 staged、unstaged 和 untracked；
5. 基线合并或 Retarget 后重新分析哪些行为可能受影响。

### 选择最小充分证据

不存在适合所有提交的固定本地全套。每个行为变化都应选择最窄、能够在回归时失败的测试或门禁：

- 包或脚本行为：拥有该行为的聚焦测试；
- 跨包契约：相邻消费者测试；
- 文档、目录和注释：文档同步、链接、格式和 Lint；
- 模型、编辑器、CLI、终端或 UI 输出：拥有该输出的快照或真实场景；
- Manifest、公共导出、构建配置、Worker/Bin：Build、包卫生和产物 Smoke；
- 真实 Provider：有凭据时运行对应 E2E，绝不打印密钥。

完整本地演练只在以下情况执行：用户明确要求、诊断 CI、或变更真正横跨仓库且无法找到可信的更窄集合。CI 负责完整覆盖率和平台矩阵。

### 聚焦测试和聚焦覆盖率是两个选择

测试文件过滤只决定运行哪些测试；覆盖率 Include 决定衡量哪些源码。两者都要与改动对应。不能用 `passWithNoTests`、降低阈值或故意缩小 Include 隐藏未覆盖文件。

动态加载、子进程、Worker、构建产物和外部 Provider 可能无法被依赖图发现，需要显式选择拥有它们的测试。

### 避免重复运行

一项检查已经在当前最终 diff 上通过后，不要仅因为马上 Commit 或 Push 就手动重复。也不要声称 Git Hook 可能运行的检查已经执行；最终报告只列真正运行过的命令。

### 失败处理

- 普通 Push 前相关检查失败：停止，修复或报告阻塞；
- 环境特定失败：记录准确命令、测试和平台差异，并证明其他相关证据；
- 需要跳过 Hook：必须得到用户明确同意，并说明为什么预计 CI 不同；
- 不要先推送再期待 CI 奇迹般通过。

### 历史重写保护

重写远程分支前：

1. Fetch 当前远程头；
2. 记录准确 OID；
3. 使用带准确期望 OID 的 `--force-with-lease`；
4. 远程移动时立即中止；
5. 禁止裸 `--force`；
6. 重写后重新 Fetch 并审计 Review Thread、Approval、Mergeability 和 CI，因为旧 Commit 锚点已失效。

### 推送后

- 验证远程引用等于本地 HEAD；
- 检查 PR CI；
- Pending 就报告 Pending；
- 失败先读日志再归因；
- 不把 Push 命令成功等同于 PR 已可合并。

### 可复用推送前提示词

```text
在推送前检查当前分支相对实时目标基线的完整出站 diff，包括已提交、暂存、未暂存和未跟踪文件。根据实际影响选择最小充分检查，不默认运行全仓库套件，也不重复已经在最终 diff 上通过的检查。

行为使用拥有它的聚焦测试；可见输出使用快照或真实场景；Manifest、公共导出、Worker/Bin 和构建路径使用 Build、包卫生与产物 Smoke；文档使用文档同步、链接、格式和 diff 检查。只报告实际运行的命令。

检查失败时停止推送并修复或报告。历史重写只允许在记录远程 OID 后使用精确 force-with-lease，禁止裸 force。推送后确认远程 HEAD、PR Review 状态和 CI，Pending 不得声称通过。
```

## 堆叠 PR 工作流

本节适用于 GitHub 或其他平台提供官方 Stack 对象和合并 API 的情况。

### 必须使用平台原生 Stack

依赖 PR 链应通过官方 Stack 对象和 Stack Merge 操作合入，不能用逐个 Merge、手工 Retarget 模拟 Stack 语义。平台应拥有顺序、CI、Retarget 和合并状态。

官方能力不可用、跨 Fork 不受支持或链条存在冲突时停止，不能悄悄降级为手工方案。

### 建立实时 Stack

- 使用干净专用 Worktree；
- 查询每个 PR 的 Base、Head OID、作者、Draft、Review、Merge State 和 Checks；
- 官方 Stack 对象是成员身份权威，不能只根据 Base 分支猜测；
- 从实时 Base 建立 bottom-to-top 顺序：底层指向 Trunk，上层指向紧邻下层 Head；
- 分页读取完整 Stack 成员。

### 链接缺失成员

已有 Stack 是期望链的保序子集时，可补充缺失成员。出现多个 Stack、意外成员或顺序冲突时先请求用户方向。

同作者且平台允许时，可以按 bottom-to-top 自动链接；作者不同或身份不可用时，改变远程 Stack 前询问。不能自动解散、重排或重建已有 Stack。

### 只在需要时刷新分支

不要因为存在 Rebase 工具就改写历史。只有合并状态或仓库规则要求更新 Trunk 时，选择项目允许的方式：

- 原生级联 Rebase/Sync，并在发布后立刻验证每层；
- 从底层向上逐层 Merge-Forward，正常 Push。

任何重写后都重新查询准确 Head、评审线程、Approval、Mergeability 和 Checks。冲突或本地/远程 Stack 结构分叉时取消并询问，不自动删除重建。

### 合并前检查

- 重新查询官方 Stack；
- 所选 PR 都是 Open、非 Draft、顺序正确；
- 每层独立满足 Review 和 Checks；
- “合入整个 Stack”表示全部成员；
- 部分合入必须明确边界，并包含从底层到边界的所有层。

### 通过 Stack API 合入

调用官方 Stack Merge，而不是逐个 PR Merge。不绕过合并要求；平台报告阻塞时解决拥有该问题的 PR，或停止报告。

Queued 不等于 Merged。等待每个目标 PR 报告已合并。部分合入后，确认剩余上层仍保持正确 Stack、Base、Head、Review 和 CI。

### 删除分支

分支删除是独立最终步骤。只有 PR 已 Merged 且没有任何 Open PR 仍以该分支为 Base 时才删除。

## 技术文案与注释标准

### 保留完整命题

编辑前枚举段落里的每个事实：

- Actor 和 Action；
- 条件、时机和顺序；
- 必须、可以、禁止等强度；
- 否定保证和例外；
- 所有权、副作用、失败方式和后果。

只有这些命题都被保留且表达更清楚时，删词才是改进。字数更少本身不是质量。

### 一处事实，一个拥有者

架构、理由、算法、历史和长示例放在拥有它的文档；使用点保留调用者需要的行为、失败、时序、所有权和后果，并链接到拥有者。必要契约可以在本地重复，长篇理由不应复制。

### 各位置应写什么

- **公共 JSDoc**：返回区别、异常、拒绝、副作用、所有权、时序、取消和持久化；
- **内部注释**：非局部结构、不变量、竞争顺序、安全边界和意外失败；
- **模块注释**：角色、依赖、责任和非显然架构选择；
- **测试注释**：为什么 Fixture、间接观察、平台适配或真实入口不可缺少；
- **教程**：前置条件、操作、真实入口、可观察验证和简短警告；
- **README**：消费者配置、语义、失败、限制、扩展点和可见影响；
- **决策记录**：独有理由、机制、替代方案、后果和验证；
- **事故复盘**：事件顺序、证据、因果链、影响和预防；
- **Skill/Agent 指令**：行为护栏和明确范围边界；
- **配置注释**：访问限制、非显然接线、加载顺序、安全和回放；
- **Prompt/可见文字**：视为行为并验证输出；
- **诊断**：失败对象、违反规则和非显然修复方法。

不要注释代码已经明显表达的事实。

### 术语准确

`contract`、`boundary`、`shape`、`surface`、`seam`、`gate` 和 `vocabulary` 不是禁词，但使用前要问能否用更准确的“响应字段”“JSON 校验”“ESM 导出”“进程边界”“前置条件”等词替代。

`contract` 应保留给调用方、实现方、生产者或消费者真正依赖的前置条件、后置条件、不变量和兼容承诺。`boundary` 应指真实进程、网络、安全、事务或生命周期边界。

## 清理推理过程与评审痕迹

### 唯一判断测试

对可疑文案询问：只查看当前仓库 HEAD、无法访问 Agent 会话、PR 讨论和未提交草案的读者，能否解析所有引用并验证所有主张？如果不能，就把仍成立的事实改写为当前仓库视角，并删除会话过程。

通过该测试不代表文字一定适合 README 或 JSDoc。可解析的变更历史仍应放到决策记录、提交、PR 或事故复盘。

### 泄漏类型

1. **失效的设计会话引用**：`decision 7`、`audit C2`、未提交草案章节和阶段编号；
2. **PR/Stack 视角**：“后续 PR”“本 PR 添加”“上一提交”；
3. **变更叙述**：“以前”“现在”“不再”“旧版本”“这次改动”；
4. **评审编排**：“评审拒绝”“评审者确认”“第 5 版”；
5. **面向评审者自证正确**：“这个转换是安全的，因为……”；
6. **推导过程**：逐步复述控制流、测试走读和明显分支证明；
7. **犹豫和计划残留**：“目前应该够”“大概没问题”；
8. **语言滑移**：英文文档夹杂未翻译工作语言，或相反。

处理方式不是一律删除。段落包含事实时，先枚举并改写事实；只包含审计编号或控制流旁白时才直接删除。

### 不属于泄漏的内容

- 可在当前仓库解析的 Issue 引用和稳定 TODO 标签；
- 决策记录和事故复盘中的已合并 PR/Issue 证据；
- Lint、Coverage、空 Catch 等必须存在的抑制理由；
- 当前时态反事实：“没有 X 会发生 Y”；
- 校准常量的测量值和来源；
- 运行时旧连接与新连接等真实生命周期状态；
- 外部标准章节和可解析设计资源；
- 项目集体口吻；
- 决策记录中的替代方案。

### 修复顺序

1. 明确范围，排除 Vendor、冻结归档和记录型 Fixture；
2. 只读审计，搜索模式只是召回探针，还要人工阅读高密度文案；
3. 先修改拥有者：生成目录改源码/模板，类型摘录改源 JSDoc，多语言成对更新；
4. 模型可见文字属于行为，不能静默改写；
5. 删除前枚举命题，防止把义务改成建议、把假设改成已发布能力、删除真实事实或丢失测量来源；
6. 重新搜索残留并运行对应门禁。

## 文档信息架构

### 先确定文档结构，再润色句子

对每份人类文档：

1. 确定它在目录树和导航中的位置；
2. 确定其自身主题和直接子主题；
3. 设定允许的细节层级；
4. 判断它是教程还是参考；
5. 教程按前置知识和难度排序；
6. 大量混合教程/参考内容应拆分，少量次要内容用明确章节标记；
7. 将后代模块拥有的细节移到对应文档，当前层只保留目的、责任和高级行为及链接。

### 一条事实只有一个层级拥有

通用层级可以这样划分：

| 层级 | 职责 |
| --- | --- |
| 根 `AGENTS.md` | 每次任务都需要的短常驻命令，链接详细规则 |
| 子树 `AGENTS.md` | 只对该目录生效的补充规则 |
| 架构文档 | 系统组成、核心模块、数据流和扩展点 |
| 子系统参考 | 类型、Schema、API 和语义 |
| 决策记录 | 为什么这样做、放弃了什么、需要什么验证 |
| 事故复盘 | 事故时序、证据、因果和预防 |
| Cookbook | 编号步骤和可观察验证 |
| 用户文档 | 产品使用方式 |
| 包 README | 单包消费者契约 |
| Skill | 可复用工作流和专项判断标准 |

### 教程与参考

- 教程带领读者按顺序达到可观察结果，只在当前步骤引入必要概念；
- 参考资料定义可查找范围和当前行为，不要求顺序阅读；
- 写教程前私下判断读者起点和每个概念的初级、中级、高级程度；
- 高级可选内容放到后续教程或参考，不提前阻塞主路径。

### 文档预算

字数上限是防止内容无边界增长的护栏，不是删字目标。超预算时按顺序：

1. 移走属于其他层级的内容；
2. 压缩属于本层但可更短的内容；
3. 内容确有必要时提高预算，并在评审中解释。

不能为了通过预算删除必要契约。预算内也应保留一定增长空间。

### 文档 Slop 检查

- 同一规则在多个地方重复；
- README/JSDoc 叙述“过去、现在、改名、移动、PR”；
- 手写实现状态和未来状态，最终会腐烂；
- 手抄源码、测试、包和 JSDoc 目录；
- 推理过程、测试走读和明显控制流；
- 兄弟方法旁重复相同理由；
- 一个段落塞入多个规则和大量括号；
- 到处加粗、大写和“至关重要”；
- 已实施决策记录仍使用“应该、计划、验收清单”等提案语言。

### 机器可检查链接

仓库引用使用相对 Markdown 链接，避免只写裸文件名、编号或不可解析描述。移动文档时先搜索入站引用，原位置删除、新位置添加、索引和链接修复必须原子完成。

## 双语文档与翻译工作流

### 调用边界

扩展翻译工作流只在用户明确要求时运行，不能从普通文档修改自动升级成全量重译。日常小改遵循最小配对更新。

两个语言版本具有同等权威；本次被编辑的一侧是本次更新的源。不能永久指定某一种语言为唯一人工源，除非该文件明确由生成器拥有。

### 按变化类型分流

- **已有配对，单侧修改**：生成变更简报，只更新另一侧对应语义单元；
- **全新配对**：按整篇翻译流程创建；
- **删除或改名**：另一语言和一致性记录一起删除或改名；
- **两侧同时变化或结构无法对齐**：人工整篇协调，不能自动拼接；
- **冻结归档**：不翻译、不重录、不修复。

### 最小更新路径

简报应包含：

- 自上次确认一致以来的源侧 Diff；
- 改变的段落、表格行、列表项或章节；
- 上次确认源文本；
- 当前源文本；
- 当前对应译文；
- 涉及术语；
- 首次出现注释是否移动；
- 绑定结构规则。

只有代码 Fence 发生机械变化时可以由工具安全同步。正文变化由翻译者使用最小覆盖 Diff 的修改，保留未改变且已评审的措辞；不能为了小改重译整篇。

### 全文翻译三遍法

1. **按语义单位自然重写**：以目标语言技术作者口吻表达，不逐词转置；
2. **逐条与源文核对**：不添加、不删除，术语一致，代码和机器 Token 保持；
3. **脱离原文单独阅读译文**：修复只有独立阅读时才能察觉的别扭表达。

只写最终稿，不把草稿和翻译笔记写进文件。

### 结构和格式保护

- 标题层级与顺序一致；
- 列表类型、起始编号和条目数一致；
- 表格行列数一致；
- 链接目标一致，只翻译显示文字；
- 代码 Fence 的 Info String、空白和注释逐字节不变；
- Inline Code、命令、Flag、路径、标识符、事件、配置键和协议值不翻译；
- 强调标记类型和覆盖范围不随意改变；
- 语言切换行按目标文件方向翻转。

### 忠实度

必须保留：Actor、Object、条件、例外、否定、强度、因果、完成条件、生命周期、结果通道、所有权变化和数量边界。流畅不能成为丢失事实的理由，完整也不能成为逐字僵硬翻译的理由。

### 术语治理

术语表是双向约束，不是建议。翻译前加载，不等遇到陌生词才查。未收录术语优先查可信开源项目或供应商先例；无法确定时保留原文并列入待定术语，不在段落中临时造词。

评审决定新的标准译法时，更新术语表，而不是只修复单个文件。

### 一致性记录

完整配对可由伴随文件记录两侧 Blob Hash。重新记录意味着翻译者人工确认当前两侧语义一致，不能把机械写 Hash 当作证明翻译正确。结构、链接和 Hash 门禁也不能代替人工语义审查。

### 自动翻译 Prompt 的通用协议

自动翻译模型的指令优先级：

1. 保留源文语义、结构、受保护内容和格式；
2. 严格遵循注入术语表；
3. 使用整篇人工金标配对校准语气，不当作翻译记忆；
4. 应用一般文风和示例。

输出采用三阶段结构：

```xml
<translation>
完整初稿
</translation>
<review>
逐类复核发现和实际修正；无修正时输出固定标记
</review>
<final>
修正后的完整最终文档
</final>
```

复核覆盖结构、忠实度、语气、句法、词汇、术语和目标语言标点。流水线只解析 `<final>`，真实请求一次翻译整篇；Few-shot 使用人工评审过的整篇文档对，而不是孤立句子。

### 可复用翻译提示词

```text
将完整源文从 {{source_lang}} 翻译为 {{target_lang}}。先按完整语义单位理解并以目标语言技术作者口吻自然重写，再逐条核对源文：保留每个命题，不添加任何命题。

优先级依次为：源文语义与结构、术语表、整篇金标的文体、一般写作建议。低优先级规则不得覆盖高优先级要求。

保持标题、列表、表格和链接结构。代码块逐字节不变，包括注释；Inline Code、命令、路径、标识符和协议值保持原样。保留 Actor、条件、例外、否定、强度、因果、生命周期、结果通道、所有权和数量。

译文应像目标语言技术作者原创，不逐词转置。最后脱离原文单独阅读并修正不自然表达。用 translation、review、final 三段 XML 输出，final 必须包含完整最终文档。
```

## 文档网站同步

### 仓库 Markdown 是唯一可编辑源

文档网站应被视为经过测试的投影：清单选择公开页面，投影器生成网站临时树，站点工具构建该临时树。不要直接编辑或提交生成目录、缓存和构建输出。

多语言文件继续按仓库配对规则共处，不因网站路由另建语言源目录。源文件布局和公开路由树可以不同，由投影器负责映射。

### 分类变更

- 已发布页面正文修改：只改 Canonical Markdown；
- 新页面：先放入正确文档层级，再添加一条公开清单；
- 改名、移动、删除：源文件、清单和入站链接原子更新；
- 生成目录：改生成器或源元数据，不手改；
- 网站结构：普通页面只改清单，现有模型无法表达时才改站点配置。

公开清单是明确 Allowlist。不要因为内部 RFC、复盘、测试指南或 Agent 指令位于 `docs/` 就自动发布。

### 清单字段

通用页面清单可包含：

- Canonical Source；
- 公开 Route；
- 导航 Label；
- Sidebar；
- Section；
- 同 Section 稳定排序；
- 额外 Source Alias；
- 语言配对或回退策略。

每个字段显式填写。新增 Section 时同步导航顺序。Alias 只帮助解析源链接，不自动创建另一条公开路由。

### 链接投影

- 清单内目标转换为站点路由；
- 仓库内但未公开目标转换为源码链接；
- 图片复制到生成树；
- 外部、绝对、邮件和仅 Fragment 链接保持；
- 缺失相对目标让构建失败，不静默产生坏链；
- 标题 Fragment 不一致时在源文或生成器添加稳定 Alias；
- 不为迎合站点，在 Canonical Markdown 中写网站专属路径。

### 验证和部署边界

本地预览后运行站点 Focused Gate、文档同步、Lint 和 Diff 检查。报告 Canonical 文件、清单项、公开路由和实际命令。

内容同步到可构建站点不等于互联网部署。没有用户明确要求和 Hosting Policy 确认时，不添加 Pages 权限、部署 Workflow、域名或公开托管。

## 决策记录生命周期

### 决策记录的职责

决策记录保存代码和普通文档无法长期承载的内容：为什么这样决定、拒绝了什么、付出什么代价、需要什么验证、何时可能重新讨论。

非平凡变更应新增或更新至少一份拥有该决定的记录。纯机械或局部、且不改变行为、契约、结构、流程或理由的编辑可以豁免。

### 双轴目录

建议路径同时编码生命周期和分类：

```text
<lifecycle>/<class>/yyyy-mm-dd-topic.md
```

生命周期：

- `proposed`：尚未实现或只部分实现；
- `implemented`：已经发布，正文保持与当前实现一致；
- `rejected`：提案被拒绝，只在理由仍能阻止有吸引力的错误时保留；
- `archived`：已实施但未来决策价值低的冻结历史。

通用分类：功能、缺陷修复、精简、架构、流程、测试。分类集合应由脚本或 Schema 约束，避免随意新建近义目录。

### 什么时候写

以下变化通常值得记录：

- 产品行为；
- 跨文件或跨包契约；
- 架构和能力边界；
- 持久化、网络和配置格式；
- 流程、工具和测试策略；
- 维护者未来可能重新讨论的取舍。

已有记录拥有该主题时更新它，不创建重复记录。不能把已实施记录直接改写为相反决定；反转需要新记录和交叉链接。

### 统一格式

提案：

```markdown
# 决策记录：<标题>

Status: proposed

## 问题
## 提案
## 替代方案
## 验收标准
## 风险
```

已实施：

```markdown
# 决策记录：<标题>

Status: implemented

## 问题
## 决定
## 替代方案
## 后果
```

拒绝记录保留提案内容，并在 Status 行写简短拒绝原因。

所有记录都必须写真实替代方案以及它们为什么落选。没有替代方案的决定会不断被重新诉讼；不能为了满足模板凭空编造历史上没有考虑过的方案。

### 生命周期移动

`proposed` 移到 `implemented` 时：

- Proposal 改写为现在时的 Decision；
- 验收标准和风险融入后果、测试或验证；
- 删除未实施计划，记录实际发布内容；
- 路径、名称、默认值和机制保持与当前代码一致。

`proposed` 移到 `rejected` 时只需记录拒绝原因并冻结提案事实。

### 保持已实施记录当前

后续代码移动文件、重命名符号或改变现有决定的实现位置时，同一改动更新已实施记录中的事实。只更新事实实现，不重写原决定和理由。真正反转决定需要新记录。

### 归档判断看未来价值，不看年龄和字数

保留活跃记录的理由：

- 替代方案仍可能被重新提出；
- 所有权或安全边界仍指导工作；
- 持久化/网络语义和负向保证仍有效；
- 重新引入条件仍重要；
- 当前实现本身无法解释为什么不能简化。

适合归档：一次性 UI 细节、狭窄适配器、已关闭小缺陷、已被权威源码取代的实现清单、未来设计价值低的流程历史。

Proposed 不归档：不再推进就明确拒绝。Rejected 只有仍能防止真实错误时保留，否则删除完整配套集合。

### 新记录触发同主题查重

新增记录时搜索同一决定、机制和失败替代方案的活跃记录：

- 完全取代且未来价值低的 Implemented 记录在同一改动归档；
- 部分取代的记录保留并交叉链接；
- 过时 Proposed 转为 Rejected；
- 无价值 Rejected 删除；
- 新拥有者吸收全部独有命题时可以按合并规则删除旧记录。

### 冻结归档

归档作为原子配套集合移动，例如正文、多语言版本和一致性记录。归档时只允许增加归档日期和机械 Hash，不更新正文、翻译或外链。修复活跃文档指向归档的入站链接，但不修复冻结记录自身的出站链接。

归档封存后不编辑、不移动、不重译、不重新格式化、不删除，也不把它当作当前行为权威。

## GUI 变更的可视化证据

### 什么时候需要

项目可以规定所有用户可见 GUI PR 必须附短 GIF 或视频。证据必须来自该 PR 的真实代码树、真实服务器和真实产品流程。除非用户明确要求 Fixture 演示，不能用 Mock 传输、测试 Hook、合成事件或静态 Fixture 冒充真实体验。

紧邻媒体写明：

- 被演示的 Commit SHA；
- 提供服务的代码树和来源；
- Build/Dev 模式；
- 配置覆盖和浏览器状态例外；
- 是否运行真实 API 或模型回合。

### 录制和发布分离

录制只产生本地 Frame 和媒体文件，不改变远程状态。上传资产分支和修改 PR 正文是独立最终步骤，只有任务明确要求附到 PR 才执行。

凭据或服务器不可用时报告限制，不能偷偷换成 Fixture。永远不读取或展示凭据值，使用应用正常配置路径和无害演示输入。

### 为目标 Commit 准备隔离环境

1. 要求干净 Worktree；
2. 记录准确 HEAD；
3. 从该树构建；
4. 使用新的应用 Home、工作区、会话和端口；
5. 浏览器使用新 Context/Profile，无法新建时清理该 Origin 的 Cookie 和存储；
6. 一条 Storyboard 的所有 Frame 来自同一服务器和同一隔离运行；
7. 自动化失败后丢弃旧 Frame，从新状态重跑，不能拼接不同运行。

### 录制状态，不连续录屏

- 选择三到六个能讲清故事的语义状态，例如输入、运行、完成和详情；
- 每帧使用同一 Viewport 和 Crop；
- 文件名按顺序排序；
- 截图前等待唯一、具体 UI 条件，而不是固定延时；
- 完成条件使用精确文本或稳定 DOM 标记，避免用户输入回显造成子串误判；
- 工具调用、拒绝和恢复场景需要展示工具身份、状态/稳定错误码和下游结果；
- 瞬时状态在同一次浏览器脚本中轮询标记并截图；
- 不录制密钥、个人数据、无关标签页和系统通知。

### 确定性编码和验证

编码器应校验：

- 至少两帧；
- 尺寸一致；
- Duration 数量正确；
- FPS、宽度、颜色和字节上限合法；
- 默认不覆盖已有输出；
- 最终时长和大小符合预期。

大文件先降宽度，再调整颜色或 FPS，保持文字可读和最终状态停留足够时间。

验证编码后的媒体本身，不只看源截图。检查帧数、尺寸、时长、大小、顺序、最终停留和敏感信息。查看器无法播放时，反解代表帧核对。

### 资产分支

二进制媒体不进入会合并到长期分支的 PR 分支，以免永久膨胀历史。使用只保存媒体的独立 Orphan Assets Branch，并在临时浅 Clone 中追加提交。

发布前验证：

- 分支只含媒体；
- 远端文件 Checksum 等于本地已验证文件；
- HTTP 响应、Content-Type 和大小正确；
- 修改 PR 正文前后 PR Head 仍等于录制 Commit；
- Markdown 渲染结果确实包含图片。

资产分支只追加，不删除、不重写、不 Force Push，因为已合并 PR 永久引用其 URL。

## 插件和 UI 架构细则

本节来自 DeepSeek Harness 的插件包和 Web Client 子树规则，适用于采用插件化 UI 的项目。

### Service Definition 面向所有当前 Consumer

工具 Schema、Loader、UI、传输和 Provider 特定行为留在对应 Consumer 或 Provider。不能让某一个 Consumer 定义整个通用 Service。反向气味是：只有一个内部调用者却增加公共 Service 方法；此时优先向该 Consumer 传入私有能力闭包。

### 一次异步操作一个生命周期控制器

Readiness、Cancellation、Disposal、Reservation 和 Sentinel 状态只有在各自有独立所有者或结算点时才分开，否则折叠到一个操作控制器，同时保留真正需要的回滚、回调隔离和静止保证。

### UI 插槽既是声明也是授权

组件只能渲染注册时明确声明的子插槽。重复声明或渲染未授权插槽应在加载时失败，不能通过全局查询绕过。插槽名反映组合路径而非实现类名。

### 可变 UI 数据只有有限通道

- 父级已知：Owner Props；
- 仅组件自身知道：Local State；
- 跨组件共享或 Remount 后保留：显式 Store；
- 外部可变事实：框架绑定的 Reactive Hook；
- 派生数据：对现有事实的纯函数，不建立第二订阅。

业务组件不手写外部订阅、不镜像外部 Snapshot 到第二个 Store。渲染读取的外部可变事实必须通过框架 Hook；事件处理器可以按契约读取即时 Snapshot。

### Store 所有权

Store 通过 Factory 创建，禁止模块级单例 Handle。组件通过只读 Hook 读取，通过声明的 Actions 写入。多个注册共享 Store 时，由插件 `apply` 创建一次并显式传递。

### 业务组件看不到容器 Context

依赖注入 Context 只存在于插件组装层。业务组件从 Props、Store 和 Inject Face 获得普通数据与回调，不直接获取整个 Service、容器或 React Context。需要新数据时扩展其拥有通道，不创建偷取全局 Context 的 Hook。

### 单向分层

1. **数据对象层**：拥有业务状态和连接/会话生命周期，不依赖 UI 框架；
2. **渲染机械层**：把外部 Observable 绑定到 UI Hook，提供 Slot Renderer；
3. **展示组件层**：只消费 Props，可整体替换，不拥有业务状态。

展示状态不能污染持久化业务日志。需要回放的业务事实进入权威日志，纯绘制数据由当前 Frame 或回放重新计算。

### 发布值和通知

谁重建发布值，谁在同一步通过同一 Source 发布。Observable 对象身份保持稳定；事实未变化时 Snapshot 引用保持稳定。可能晚于 Consumer 注册的路径在注册时也要通知现有 Consumer。

### UI 公共导出

UI 插件只导出加载所需入口、公开类型和必要 Store Factory 类型。组件、Helper、常量和 Store Handle 保持内部。为让测试编译而增加公共导出是错误做法；同包测试直接导入内部路径。

## 原生沙箱和发布安全

### Fail Closed

安全沙箱创建规则失败、内核不支持或探针不通过时，非零退出且绝不执行目标命令。禁止自动退化为无约束运行。

### 安全选择不由环境变量决定

负责约束进程的二进制、规则和后端不能由不可信 Ambient Environment 切换。测试注入使用函数参数或显式测试配置，生产安全选择固定在受审计配置中。

### 缩小审计面

原生安全工具尽量减少外部库和动态依赖。内核 ABI 定义、源码和构建参数成为可审计记录。CLI 的参数语法、退出码和报告行属于跨包契约，变化需要版本和 Changelog。

### 没有安装时构建回退

主机缺少匹配平台包时让探针失败并关闭能力，不在安装阶段临时编译未知二进制，也不回退到无沙箱后端。

### 发布矩阵由单一元数据源驱动

平台、CPU、允许二进制和支持矩阵使用显式受控元数据。CI 和 Release 从它生成，其他脚本不手抄平台列表。

每个架构在原生 Runner 构建。打包前验证二进制存在、可执行、架构正确；安装后验证发布 Tarball 中的字节与工作区构建一致。

不要假定不同包管理器的 Pack 行为相同；权限位、Symlink 和可执行文件必须在安装副本上验证。

## Vendor 与示例代码

### Vendor

- Vendor 是固定上游版本的源码副本；
- Manifest 记录上游 Commit 和本地补丁；
- 更新按同步流程执行，重新应用或明确退休本地修改；
- 普通代码审计和文案清理默认排除 Vendor；
- 不把 Vendor 的风格问题当成本项目自由重构范围；
- 更新后运行拥有该 Vendor 的测试和构建。

### 示例保持薄

可复用逻辑进入正式包，接受覆盖率、文档和发布门禁。示例只保留配置接线、演示资产以及 E2E/快照场景，启动胶水由正式应用包拥有。

每个示例至少包含：

- 无密钥 Smoke：通过真实 Loader/入口启动并验证输出和干净退出；
- 有密钥 Smoke：发送真实模型或供应商请求，从外部验证结果；无密钥环境自跳过。

示例配置只注释非显然接线、加载顺序、回放、安全边界和作用域，不复述可见配置项。测试目录和脚本是权威清单，不在文档手抄测试库存。

## 通用根级 AGENTS.md 模板

下面的模板将 DeepSeek Harness 的常驻规则压缩为适合放在项目根目录的命令层；详细理由应链接到拥有文档，避免把根指令写成百科全书。

```markdown
# AGENTS.md

修改代码前先阅读 README、架构文档和当前目录适用的子树 AGENTS.md。

## Git 与工作区

- 开始任务先检查 git status 和远程基线，保护用户已有改动。
- 不覆盖、回滚、格式化、暂存或提交任务范围外文件。
- 禁止裸 force push；授权的历史重写使用记录远程 OID 的 force-with-lease。
- 只报告实际运行过的检查；Pending 和未运行不得声称通过。

## 实现

- 优先使用现有能力和扩展点，不在核心循环堆积 Consumer 特定行为。
- 每个公共 API、抽象、状态机、配置和兼容路径必须有当前生产消费者或明确契约。
- 注册和副作用必须可逆；Dispose 必须等待资源静止。
- 状态只在操作成功提交后发布；缓存和视图从权威事实源派生。
- 在最终执行点实施权限和限制；Prompt、Schema 和包装器不是安全边界。
- 强类型同进程值无需重复校验；解析、配置、文件、持久化、Worker、进程和网络边界必须验证。
- 不手工实现已有标准库或健康依赖能净替换的基础设施；依赖替换必须计算完整治理成本。
- 配置错误尽早失败，不静默跳过。

## 测试

- 根据 diff 运行最小充分检查；CI 负责完整平台矩阵。
- 优先真实实现，只 Mock 昂贵或不确定边界。
- 端到端验证外部世界，不相信 Agent 自述。
- 产品可见变化测试真实入口；模型、协议或用户可见变化更新可重放快照。
- 覆盖率必要但不充分，未覆盖代码也可能应被删除。

## 文档

- 行为、配置、错误、协议和公共类型变化同步 README、JSDoc 和拥有文档。
- 一个事实只有一个详细拥有者，其他位置保留必要本地契约并链接。
- 文档描述当前状态；变更历史进入 Commit、PR、决策记录或事故复盘。
- 注释说明非显然契约、所有权、时序、安全和失败，不复述代码或 Agent 推理。
- Prompt 和用户可见文字属于行为，修改时验证输出。

## 决策记录

- 非平凡行为、架构、跨模块契约、格式、流程或测试策略变化新增或更新决策记录。
- 记录问题、决定/提案、真实替代方案、放弃的能力、后果和验证。
- 已实施记录保持当前事实；反转决定新建记录并交叉链接。
- 归档记录冻结，不作为当前行为权威。

## 安全

- 不读取、打印或提交密钥。
- 沙箱和安全后端失败时 Fail Closed，不回退到无保护执行。
- 破坏性操作前解析准确路径，符号链接与真实目录分别处理。
- 派生进程使用最小环境和私有随机临时路径。
```

## 最终使用建议

不要把本文整篇无条件塞入每次模型请求。更可靠的做法是：

1. 根 `AGENTS.md` 只保存每次任务都必须知道的短常驻命令；
2. 子树规则只在修改对应目录时加载；
3. 测试、评审、翻译、文档站、PR Stack 和 GUI 证据各自成为按需 Skill；
4. 工具说明由工具 Schema 和工具拥有者贡献；
5. 决策理由留在 ADR/RFC，而不是反复复制到 Prompt；
6. 所有模型可见稳定文字用快照固定；
7. 动态策略作为独立上下文记录并在执行层强制；
8. 修改任何提示词后，从模型视角检查最终组装结果，而不是只检查源字符串。

这套结构的价值不在于提示词更长，而在于每条规则都有明确拥有者、作用域、触发条件、执行边界和验证方式。
