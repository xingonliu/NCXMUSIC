# 精简冗余代码

## 文档定位

本文是一套供代码 Agent、维护者和审查者共同使用的“删除式精简”工作规范。它用于把“看看项目里有什么可以删”这种宽泛请求，转换成有调用证据、有行为边界、有风险说明、可独立实施和验证的精简提案。

本文以 DeepSeek Harness 的 [`dsh-find-simplifications`](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-find-simplifications/SKILL.md) 为主要来源，并将其中只适用于 DeepSeek Harness 的 Agent Loop、ACP、LLM 双适配器、双持久化后端、Cordis Loader、Agent Notes 目录和固定校验命令等规则，替换为可适用于任意代码仓库的发现式规则。原规范的核心判断、证据门槛、信任边界、生命周期分析、依赖替换、决策记录治理、分支合并和 PR 校验要求均保留。

这不是鼓励 Agent 尽可能多删代码的清单。目标是减少不再产生价值的接口、状态、分支、抽象、包边界和维护责任，同时保存仍然承担产品行为、兼容义务、安全边界或架构意图的部分。宁可提交少数证据充分的候选项，也不要输出大量只凭直觉判断的“可能冗余”。

## 从专属规则到通用规则的映射

| DeepSeek Harness 中的专属对象 | 本规范中的通用替代 |
| --- | --- |
| `AGENTS.md`、`docs/architecture.md`、防御模式和测试规范 | 当前仓库的 Agent 规则、贡献指南、架构文档、安全规范、测试规范和产品基线 |
| Agent Notes / RFC 树 | ADR、RFC、设计文档、提案目录、Issue、变更日志或仓库实际采用的决策记录体系 |
| 双 LLM 适配器、双持久化后端 | 被架构文档明确保护的并行实现、平台后端、协议适配器或容灾实现 |
| Agent Loop、Session Log、ACP、LLM、Bash | 领域逻辑、状态与持久化、协议与 UI、外部服务与工具执行、平台进程与脚本 |
| `packages/*/src` 和 Cordis Loader 路径 | 从构建配置、入口文件、工作区清单、路由、依赖注入、插件和动态加载配置发现的生产代码语料库 |
| `.agents/notes/<lifecycle>/<class>/...` | 仓库已有提案目录；若不存在，可默认采用 `docs/simplification/<status>/yyyy-mm-dd-topic.md` |
| `pnpm run doc-sync` 等固定命令 | 从当前仓库的包管理器、构建清单、CI 和贡献指南中发现的原生校验命令 |
| 对 `origin/master` 比较 | 对远程默认分支或目标合并基线比较，不能假定分支名一定是 `master` |

## 基本原则

### 证据优先于观感

代码很长、命名不喜欢、抽象层很多或某个目录看起来陈旧，都不是删除依据。Agent 必须找出符号、配置、事件、协议字段和运行入口的实际消费者，并阅读调用点的语义。

静态工具只能生成线索，不能直接生成结论。未使用代码检测器可能看不到动态导入、反射、依赖注入、字符串事件、模板引用、路由注册、原生桥接、序列化协议、插件清单、构建时入口和外部消费者。

### 测试不是不可质疑的真理

测试可以证明当前实现被某个断言固定，但不能单独证明该行为仍然值得保留。如果生产代码没有消费者，而测试只是穿透私有状态、伪造不可能出现的对象或保护废弃 API，那么测试本身可能也是待删除表面积的一部分。

删除测试前仍须解释它保护的行为、该行为是否存在其他消费者，以及删除后由什么更接近真实使用路径的验证替代。不能用“测试不重要”跳过风险分析。

### 文档和历史提案也不是不可质疑的真理

ADR、RFC、设计文档和历史提案记录的是某一时点的判断，不等于当前实现必须服从旧文本。如果代码、产品方向和兼容条件已经改变，应修正文档；但旧文档中仍然有效的动机、替代方案、失败经验和重新引入条件必须被迁移到当前决策记录，不能随代码一起无痕消失。

### 净删除行数不是唯一目标

真正的精简可以表现为：

- 更少的公共 API；
- 更少的状态表示和事件种类；
- 更少的生命周期所有者；
- 更少的配置组合与运行分支；
- 更小的协议和持久化格式；
- 更少的包、进程、适配器或兼容层；
- 更少的专用测试、快照和文档维护责任；
- 更容易解释和验证的行为。

一次重构即使新增行数与删除行数相近，只要它确实减少了状态、契约或所有权，也可能是有效精简。反过来，把复杂逻辑移动到新包装器、生成文件或第三方胶水中，即使统计上删除很多，也不一定减少了复杂度。

### 区分清理与产品决策

如果某个能力存在真实生产调用者，删除它通常属于产品范围或兼容策略变更，而不是普通冗余清理。Agent 可以报告该能力成本过高，但必须将候选项标记为“需要产品决策”，说明现有用户、调用路径和将被放弃的行为，不能自行删除。

### 先确定兼容阶段

审计前必须确定项目处于以下哪种阶段：

- 未发布或明确允许破坏性变更；
- 已发布但仍处于快速迭代期；
- 承诺语义化版本兼容；
- 存在持久化数据、网络协议、插件生态、公共 SDK 或外部脚本消费者；
- 存在法规、审计、安全或迁移义务。

同一个“无人调用”接口，在未发布应用里可能可以直接删除，在公共 SDK 中则可能需要弃用周期、迁移说明和主版本发布。仓库内部搜索不到调用者，不等于仓库外没有消费者。

## 开始前建立仓库上下文

### 保护工作区

开始任何调查或写入之前：

1. 阅读当前目录及父目录适用的 `AGENTS.md`、`CLAUDE.md`、贡献指南或同类规则。
2. 执行 `git status`，识别并保护用户已有改动。
3. 按仓库规则检查远程更新；存在未提交改动、分支分叉或可能覆盖用户工作的情况时，不进行破坏性同步。
4. 记录当前分支、目标基线和审计范围。
5. 除非用户明确要求实施，第一阶段只调查，不修改生产代码。

### 阅读产品与架构约束

至少检查：

- README、产品范围、路线图和发布说明；
- 架构图、模块边界、进程模型和数据流；
- 入口文件、路由、菜单、命令、任务调度和启动配置；
- 工作区、包管理、构建、打包和发布配置；
- 测试策略、安全规范和防御性编程约定；
- ADR、RFC、设计提案、Issue 和历史迁移文档；
- 公共 API、插件接口、序列化 Schema、数据库格式和网络协议；
- 第三方或衍生源码的许可证、上游固定版本和本地改写边界。

不要只阅读准备删除的文件。一个在本目录看似无用的类型，可能由远端进程、配置加载器、构建插件、模板、原生模块或另一个工作区包消费。

### 建立“受保护设计”清单

从架构文档和已实施决策中找出明确保留的设计，例如：

- 多平台实现；
- 主备后端；
- 两种协议或供应商适配器；
- 离线与在线执行路径；
- 兼容旧数据的读取器；
- 安全隔离进程；
- 为测试替换而存在的能力边界；
- 有明确恢复目标的回滚路径。

默认不能把这些并行实现当作“重复代码”整块删除，除非用户明确改变了产品约束，或新证据足以推翻原决策。受保护边界内部没有消费者的方法、事件或钩子仍可成为候选项，只要删除不会破坏被保护的架构意图。

## 什么是强精简候选项

强候选项应删除、合并、降级或重新归属真实存在的表面积，并能证明当前设计成本大于收益。

### 无生产消费者的表面积

- 公共方法、导出、事件、配置项、功能开关、注册表通知或辅助函数没有生产消费者；
- 某个包、进程、命令或入口没有真实启动路径；
- 某个持久化事件、协议字段或 Schema 分支从不被写入或读取；
- 只有测试、文档、示例、快照或生成预期文件消费该行为，而且该行为并不承担真实契约。

### 重复表达同一事实

- 持久化状态与内存事件分别保存相同事实；
- Store、缓存和领域对象互相镜像，却没有不同一致性需求；
- 同一运行状态由布尔值、枚举、Promise 和事件同时表示；
- 原始数据和派生摘要都可写，导致双写、回滚和一致性保护；
- 两份快照或基准文件在规范化后始终相同；
- 两套配置默认值、字段映射或错误分类表达相同规则。

目标不是机械合并所有重复数据。若两份表示服务不同信任边界、持久化周期、性能预算或兼容格式，应保留并说明差异。

### 没有消费者的能力边界

- 接口要求每个实现都提供某些方法，但调用方从不使用；
- 抽象基类、Port、Repository 或 Service 暴露了“未来可能需要”的操作；
- 注册器、扩展点、回调或 Hook 只有注册端，没有生产订阅端；
- 一个能力只被测试直接穿透，而真实产品通过另一条更窄的路径工作。

一个无人据此编程的抽象方法不是有效边界，而是所有实现都必须维护的推测性表面积。

### 推测性产品通用能力

重点审查没有当前产品所有者或使用场景的通用性，例如：

- 实际只使用单实例，却维护多实例编排；
- 没有恢复入口，却维护完整加载、恢复或迁移 UI；
- 没有后台任务产品需求，却维护任务名册、暂停、恢复和跨会话归属；
- 没有动态扩展需求，却维护运行时热注册和失效广播；
- 没有用户入口，却维护复杂的中途转向、撤销、重试或多阶段交互；
- 所有调用者都使用同一策略，却保留大量未使用配置组合；
- 只存在一个实现，却为了未知未来提前建立多层工厂、适配器和策略。

一旦发现生产调用者，这类候选项应升级为产品决策，不再按普通死代码处理。

### 只为废弃表面积存在的防御和测试

- 不变量、回滚路径、补偿事务只保护已无人调用的 API；
- 特殊错误类型和错误恢复只服务已废弃分支；
- 期望输出、Golden、Fixture 或端到端场景只验证不再支持的功能；
- 防御性复制、冻结、Getter 陷阱或回调捕获只防范同进程类型系统已排除的伪造对象；
- 兼容适配层的上下游都已删除，只剩适配层自己的测试。

不能因为测试复杂就直接删除。必须先证明被保护的生产契约已经不存在，或存在更窄、更真实的替代验证。

### 仅为支持代码形成的边界

- 单独发布的包只包含测试、演示、Fixture 或脚本支持代码；
- 包拆分没有隔离、复用、所有权或发布价值，却增加版本、依赖、构建和文档成本；
- 示例应用复制主应用的大量启动胶水，而不是作为薄叶子组合真实包；
- 静态目录清单、手写索引或生成目录与构建系统已有事实源重复。

### 手写基础设施可由标准能力替代

协议解析、分帧、重试与退避、Glob、Diff、队列、缓存、Schema 校验、命令行解析等基础能力，应检查目标语言标准库、运行时内建能力或成熟依赖是否已经覆盖。

依赖替换只有在删除原实现、专用测试和说明后仍获得净简化时才成立。把同样复杂度搬进包装器或适配胶水不算精简。

### 行为略有变化但更合理

精简不要求所有边缘行为逐字节保持一致。如果旧行为没有明确消费者，新行为合理、可解释且减少了大量状态或特殊分支，可以作为候选项，但必须公开行为差异、兼容风险和回退策略。

## 什么不是强候选项

以下情况通常不足以单独形成持久化精简提案：

- 修正一个错别字或删除几行显然无用的局部变量；
- 只运行一次 `knip`、编译器或 IDE 检查就断言可以删除；
- 删除架构文档明确要求保留的后端、平台或适配器；
- 只说“这里看起来复杂”，没有调用点和所有权证据；
- 只减少文件数量，却没有减少公共契约或必需行为；
- 用新的抽象层包住旧复杂度；
- 为追求行数，把容易理解的代码压缩成隐晦技巧；
- 把仍有外部消费者的公共 API 误判为仓库内死代码；
- 把短期重复误判为可合并，却忽略不同发布周期、安全边界或并发所有者。

小而明确的局部问题可以直接修复，或按仓库约定记录带稳定标签的 TODO；不要为每个微小清理制造一份架构提案。

## 广度审计方法

### 按领域分区调查

需要广泛调查或多个候选项时，将仓库拆成相互独立的审计域。可并行使用多个 Agent，也可由单个 Agent顺序模拟。每个审计域都必须提交证据而不是猜测。

通用审计域包括：

- 领域与应用服务：命令、查询、工作流、用例和聚合边界；
- 状态与持久化：事件、缓存、数据库、迁移、恢复、重放和派生数据；
- UI 与交互：路由、页面、弹窗、状态映射、展示模型和不可达入口；
- 协议与进程边界：IPC、HTTP、WebSocket、消息队列、Worker、子进程和原生桥接；
- 外部能力：模型、支付、存储、搜索、媒体、系统 API 和供应商适配器；
- 工具与任务执行：前后台分支、任务归属、取消、输出缓存、临时文件和执行器接口；
- 包与模块：工作区拆分、公共导出、循环依赖、支持包和重复启动胶水；
- 配置与扩展：功能开关、环境变量、插件、注册表、动态加载和默认值；
- 测试与产物：重复 Fixture、Golden、快照、Mock、测试专用接口和生成文件；
- 脚本与发布：废弃 CLI、构建入口、迁移脚本、发布清单和平台分支；
- 文档与决策记录：已被实现取代、功能已删除或互相重复的提案与说明。

不要因为找到第一个好候选项就停止整个广度调查。先完成约定范围的扫描，再对候选项排序。

### 从成本最大的区域开始

除了明显的未使用符号，还应优先查看：

- 最近长期高频修改的生产文件；
- 历史提交中反复新增又删除的模块；
- 代码量、分支数、依赖数或测试量最大的基础设施；
- 故障修复经常触及的生命周期与并发代码；
- 为一个功能维护多份状态和兼容逻辑的区域；
- 发布、打包或启动链路中层层转发的配置。

广度审计如果只停留在浅层死符号，会错过真正承担维护成本的重复生命周期和防御机制。

### 使用历史帮助理解，不以历史代替证据

可使用 `git log -- <path>`、`git log -S<symbol>`、`git log -G<pattern>` 和 `git blame` 判断某个表面积为何出现、是否曾有消费者、是否属于已添加又删除的功能。

提交日期、标题和旧分支只能作为发现线索。当前代码、配置、协议、文档和真实调用方才是保留或删除的主要证据。

## 审计信任边界

对每个防御性复制、冻结、校验器、序列化、回调捕获和异常隔离，明确回答：

1. 值来自哪里？
2. 来源是否可信？
3. 当前所有者是谁？
4. 接下来谁可以修改它？
5. 是否跨进程、跨线程、跨网络或跨持久化边界？
6. 类型系统是否真实约束运行时输入？
7. 删除防御后最坏后果是什么？

同一进程中由强类型 Service、插件或内部函数借出的只读值，通常不需要为敌意 Getter、原型污染式伪造对象或交接后任意突变建立多层防御。解析器、配置加载器、消息队列、模型或工具 JSON、持久化文件、Worker、子进程、网络解码器和原生边界则必须拥有或校验自己的数据。

围绕敌意 Getter、伪造类型对象、回调被替换或内部交接后突变建立的测试，只能说明实现曾考虑这种契约，不能自动证明契约合理。Agent 必须指出真实输入是否可能满足攻击模型。

即使当前没有已知攻击者，也不能删除安全边界中的验证。身份认证、授权、路径校验、反序列化、签名、密钥处理和进程隔离应按威胁模型判断，而不是按调用次数判断。

## 审计异步生命周期与所有权

对复杂异步代码画出所有权图，并把以下机制映射到具体所有者或状态迁移：

- 哨兵值和布尔状态；
- readiness、settlement 和 quiescence Promise；
- AbortSignal、取消路径和超时；
- disposer、close、shutdown 和资源回收；
- 当前任务、队列、Worker、进程或会话所有者；
- 首个成功、首个失败和首个终止结果；
- 发布、回滚、重试和补偿事务。

如果多个机制镜像同一个“是否活跃”“是否完成”“是否已取消”事实，应考虑由一个事务、状态机或生命周期控制器拥有它。

以下情况通常需要保留独立机制：

- 同步发布失败时必须原子回滚；
- 用户回调或第三方回调必须被隔离；
- 多个并发结果竞争首个终态；
- Worker 或子进程资源有独立所有者；
- `dispose` 必须保证系统进入完全静止状态；
- 取消当前步骤与取消整个队列具有不同产品语义；
- 持久化事实与瞬时运行状态具有不同恢复责任。

不要为了减少状态变量，把不同所有者或不同终止语义强行合并。

## 手写实现与依赖替换

引入依赖可以是精简手段，但不是自动正确的答案。仓库已有依赖政策时，以该政策为准；没有时至少评估以下内容：

- 运行时或标准库是否已提供同等能力；
- 依赖是否仍在维护，发布是否稳定；
- 实际采用度、维护者数量和安全记录；
- 直接及传递依赖体积；
- 浏览器、桌面、服务端、移动端和目标 Node/语言版本兼容性；
- 许可证、署名、供应链和离线安装要求；
- Tree-shaking、打包、冷启动和内存影响；
- 是否引入 Native 二进制或平台构建成本；
- API 是否覆盖现有语义，还是仍需大量包装胶水；
- 迁移后能否删除专用实现、测试、文档和维护知识。

证明依赖替换候选项时：

1. 阅读完整手写实现，列出依赖准确覆盖的表面积。
2. 列出依赖没有覆盖的残余语义，这些成本必须保留在提案中。
3. 检查已有决策记录，不能只用“成熟依赖优先”推翻明确保护的本地实现。
4. 计算净删除：删除的实现、专用测试和文档，减去新增适配胶水、配置和依赖治理成本。
5. 优先使用目标运行时最低版本已具备的标准能力。
6. 如果包装器只是把同一复杂度换了位置，拒绝该候选项。

## 证明或拒绝每个候选项

### 先发现语料库，不要硬编码目录

通过工作区清单、编译配置、打包配置、入口字段、路由、插件清单、依赖注入和 CI 脚本识别仓库语料库，再将消费者分为三类。

#### 生产语料库

包括实际进入构建、打包、部署或运行时加载路径的源码、配置、资源、迁移、运行脚本和生成入口。

#### 非生产语料库

包括测试、README、设计文档、决策记录、快照、Fixture、Golden、生成预期输出、注释和仅供开发的工具。

#### 用途不明确的语料库

示例、脚本、调试页面、实验目录、开发服务器和 Smoke Test 可能同时承担产品入口、发行校验或纯演示职责，必须阅读用法后分类。

### 搜索顺序

优先使用 `rg` 或等效的快速全文搜索工具：

1. 搜索精确符号名、类型名、事件名、包名、配置键和协议字符串。
2. 对方法同时搜索 `.name(`、`name(`、可选链调用、绑定和解构形式。
3. 搜索导出、再导出、类型导出和桶文件。
4. 搜索字符串注册、路由表、插件表、菜单表、命令表和 Schema。
5. 搜索动态导入、文件名约定和 Glob 扫描。
6. 搜索序列化字段、数据库列、IPC Channel、HTTP 路径和消息 Topic。
7. 搜索测试、文档、快照和历史提案中的非生产消费者。
8. 阅读每一个可信调用点，不以搜索命中数量代替语义理解。
9. 必要时检查构建产物清单、Source Map、运行日志或覆盖率，补足静态搜索盲区。

`knip`、编译器未使用检查、IDE 引用计数、覆盖率、依赖图和 Tree-shaking 报告都可以作为辅助证据，但不能替代对公共接口、动态事件、插件装载、模板引用和外部兼容面的判断。

### 为候选项建立证据表

每个候选项至少记录：

| 维度 | 必填内容 |
| --- | --- |
| 当前表面积 | 文件、符号、事件、配置、协议或包边界 |
| 生产消费者 | 调用位置、启动路径及真实用途；没有则写明搜索范围 |
| 非生产消费者 | 测试、文档、示例、快照和生成物 |
| 动态消费者 | 反射、字符串注册、插件、路由、配置、模板和外部调用风险 |
| 架构理由 | 现有 ADR/RFC/文档为何保留它 |
| 删除动作 | 删除、合并、降级、内联、重新归属或依赖替换 |
| 放弃能力 | 删除后不再支持的场景 |
| 净收益 | API、状态、分支、包、依赖、测试、文档和预计净行数变化 |
| 风险 | 兼容、数据、安全、性能、发布和未来需求 |
| 验证 | 搜索、测试、类型检查、构建、打包、迁移和人工验证 |

“未发现生产消费者”必须附带搜索范围和方法，不能只写结论。

### 结论分类

每个候选项必须归入以下一种状态：

- **推荐清理**：无生产消费者，兼容和安全风险可控，证据充分；
- **需要产品决策**：存在生产消费者或会明确缩减产品能力；
- **需要迁移/弃用计划**：仓库内可能不用，但存在公共 API、持久化数据或外部消费者；
- **保留**：当前表面积有明确、仍成立的架构或运行价值；
- **证据不足**：动态使用或外部消费无法排除；
- **局部 TODO**：问题真实但太小，不值得形成持久化提案；
- **拒绝**：净收益不足、只搬移复杂度或风险高于收益。

### 应拒绝或降级的条件

- 存在生产调用者，删除会变成功能决策；
- 已实施决策或经过事故验证的防御模式明确要求保留，而新证据不足以推翻；
- 删除会制造大量无关改动，却没有缩小公共 API 或必要行为；
- 只减少代码行数，增加认知负担、耦合或运行风险；
- 无法排除外部消费者、动态加载或数据兼容义务；
- 候选项正确但规模很小，适合直接修复或记录 TODO；
- 新依赖的供应链、体积、许可或平台成本超过净收益；
- 删除一个实现会破坏被明确保护的多后端、多平台或容灾设计。

## 精简提案的写法

### 文件位置和生命周期

优先遵循仓库已有 ADR、RFC 或提案体系。仓库没有相关约定时，可采用：

```text
docs/simplification/
├─ proposed/       # 已提出、尚未批准或实施
├─ implemented/    # 已实施，保留当前理由和验证证据
├─ rejected/       # 经调查后拒绝，保留避免重复犯错所需的理由
└─ archived/       # 已被完全取代且未来价值较低的历史记录
```

默认文件名为 `yyyy-mm-dd-action-oriented-topic.md`。一个持久化提案只负责一个可独立实施的精简决策；相互重叠的候选项应合并到实际拥有该主题的提案中，不能为追求候选数量重复建文档。

### 提案必须包含的章节

```markdown
# 精简提案：<以动作开头的标题>

Status: proposed

## 问题

说明当前 API、状态、包或行为，引用相关文件，并分别列出生产消费者、非生产消费者和动态消费风险。

## 证据

记录搜索方式、调用位置、运行入口、历史原因和现有决策文档。

## 提案

明确说明删除、合并、降级、内联、重新归属或替换什么。同步列出测试、文档、README、JSDoc、Schema、事件分类、快照和生成文件的处理方式。

## 为什么不保留

正面回答继续维护它的最强理由，以及为什么当前证据仍支持精简。

## 我们将放弃什么

说明不再支持的行为、扩展性、兼容性或调试能力，不得只写收益。

## 替代方案

列出不删除、部分删除、弃用、折叠到其他所有者或使用依赖等方案。

## 验收标准

写出可观察的最终状态、残余引用要求、测试门禁和行为验证。

## 风险与缓解

覆盖公共 API、行为变化、数据迁移、安全、性能、未来产品需求和回退方案。

## 实施范围

列出允许修改的文件或模块，以及明确排除的相邻重构。
```

提案必须具体到另一个 Agent 可以沿证据独立实现。避免“简化这个模块”“清理技术债”“减少重复代码”之类没有对象和终态的描述。

## 小型内联注释

TODO、FIXME、XXX 只用于明确、局部、无需持久化设计决策的清理：

- 使用稳定标签，例如 `TODO(double-default)`、`FIXME(dead-branch)` 或 `XXX(unused-option)`；
- 说明为什么可以安全重访，以及预期采取什么动作；
- 不为推测性抱怨添加注释；
- 需要产品、兼容或架构判断的问题必须形成正式提案；
- 如果能在当前任务中低风险直接修复，不要制造永久 TODO。

## 合并已被取代的决策记录

只有用户要求整理文档体系，或当前精简使其直接拥有的旧记录失效时，才审计决策记录。不要把每次代码精简都扩张成全仓库文档清理。

### 识别当前所有者

从已发布代码、配置、Schema、生成目录、包文档、新决策记录和入站链接中找出当前事实的所有者。日期和标题只用于发现，不能证明新文档已完全取代旧文档。

### 区分完全取代与部分取代

出现以下任何一项时，旧记录通常只是部分被取代：

- 仍有行为存活；
- 当前公共契约仍引用它；
- 持久化或网络格式仍需兼容；
- 迁移、读取或回退逻辑仍存在；
- 旧记录包含仍然独立成立的拒绝方案；
- 删除的只是某个传输、默认值、实现或展示方式，而功能本身仍存在。

仅仅可以把旧理由转移到新记录，并不表示旧记录必须保留；关键是是否仍存在独立的当前事实。

### 完全取代时的操作

1. 把旧记录中独有的动机、替代方案、后果、已发布验证证据和已知覆盖缺口迁移到当前所有者。
2. 不迁移只描述已删除实现细节、且对未来决策没有价值的清单。
3. 修复所有入站链接、索引和目录清单。
4. 将多语言版本、索引记录、一致性元数据和配套文件作为一个原子集合处理。
5. 按仓库规则归档或删除；归档文档应冻结，不在精简当前文案时重写历史。
6. 编辑后搜索精确文件名、符号、配置键、事件名和协议字符串。

### 新增后又删除的功能

只有同时满足以下条件，删除记录才能独自拥有完整历史：

- 功能已从生产代码、配置和 Schema 中消失；
- 持久化格式、网络格式、迁移和兼容行为中没有残留；
- 当前文档不再把它描述为可用能力；
- 没有测试把它当作受支持行为执行；
- 所有外部入口和生成目录已同步移除。

删除记录仍应保留：功能最初为何存在、原动机为何不再足够、完全删除之外的替代方案、放弃的能力、允许未来重新引入的条件，以及证明删除完整的证据。只验证旧实现细节的测试不属于当前验证证据；用于保证功能确实缺席的负向测试可以保留。

如果持久化数据、兼容读取、某一传输或某种展示仍存在，就不能把旧记录判定为完全失效。一个“明确不再支持某能力”的当前负向决策，即使实现已删除，也可能值得单独保留。

## 从其他 PR 或分支吸收候选项

比较兄弟分支时，应将兄弟分支与远程目标基线比较，而不是与当前功能分支比较，否则当前分支的无关差异会污染判断。

对每个候选项：

- 移植不重叠且达到证据标准的提案或 TODO；
- 将重叠内容合并到真正拥有该主题的现有提案；
- 不为了保留候选数量而移植重复或低置信度内容；
- 更新 PR 描述，准确反映候选数量、调查范围和明确排除项；
- 只有用户明确要求，或当前 Agent 明确拥有相关仓库管理职责时，才关闭重复 PR；
- 不直接复制另一个分支的结论，应重新核对它相对当前基线是否仍成立。

## 两阶段执行流程

### 阶段一：只审计和提出方案

1. 建立仓库上下文和受保护设计清单。
2. 划分审计域并完成约定范围的广度扫描。
3. 为每个线索搜索并阅读生产、非生产和动态消费者。
4. 分析信任边界、异步生命周期、外部兼容和历史理由。
5. 拒绝薄弱候选项，合并重叠候选项。
6. 按“维护成本减少、证据强度、实施范围和风险”排序。
7. 只输出证据最充分的候选项；没有可靠候选项时明确报告没有发现。
8. 为需要持久化决策的候选项撰写 proposed 提案。
9. 在用户批准前不修改生产代码。

### 阶段二：逐项实施已批准提案

每次只实施一个已批准候选项，除非多个候选项技术上不可分割且提案已经明确说明。

实施步骤：

1. 重新核对基线、工作区和提案证据是否仍然成立。
2. 确认修改范围和明确排除项。
3. 先建立或确认能覆盖保留行为的验证路径。
4. 删除或合并生产实现。
5. 删除不再成立的公共类型、导出、注册、配置、Schema 和协议字段。
6. 删除只保护废弃行为的测试、Mock、Fixture、Golden 和快照。
7. 更新仍有价值的测试，使其通过真实公共路径验证保留行为。
8. 同步 README、API 文档、架构图、JSDoc、事件表、迁移说明和生成目录。
9. 搜索被删除的精确符号、文件名、配置键、事件名和协议字符串。
10. 执行聚焦测试，再执行仓库要求的完整门禁。
11. 检查 `git diff`、`git diff --stat` 和 `git diff --check`。
12. 报告净变化、行为变化、保留能力、验证结果和剩余风险。

不要为了让旧测试继续通过而保留无人使用的兼容包装。若兼容层确有外部义务，应把任务改为弃用或迁移计划，而不是假装已经完成删除。

### 实施中的停止条件

遇到以下情况应停止或缩小范围：

- 找到此前遗漏的生产调用者；
- 发现公共 SDK、插件或外部脚本消费者；
- 发现持久化数据或网络协议仍需读取；
- 原提案把两种不同生命周期误判为重复状态；
- 删除会跨越未获授权的产品边界；
- 需要新增重大依赖、修改安全模型或改变发布策略；
- 用户已有改动与目标文件冲突，无法安全隔离；
- 验证无法区分“行为已安全删除”和“测试覆盖不足”。

停止不等于失败。应记录推翻原前提的新证据，并将候选项改为保留、部分精简、迁移计划或需要产品决策。

## 验证与 PR 卫生

### 发现仓库原生校验命令

不要复制其他项目的命令。应从以下位置确定当前仓库门禁：

- `package.json`、`pyproject.toml`、`Cargo.toml`、`Makefile` 或同类构建清单；
- CI Workflow；
- 贡献指南和 Agent 规则；
- pre-commit、pre-push 和发布脚本；
- 受影响模块自己的 README 和测试配置。

根据改动范围选择：

- 文档链接、格式和同步检查；
- 编译、类型检查和静态分析；
- 单元、契约、集成、端到端和架构测试；
- Schema、数据库迁移和兼容读取测试；
- 构建、打包、安装和 Smoke Test；
- 许可证、依赖、安全和包体积检查；
- 删除符号的残余引用搜索；
- `git diff --check` 和最终 diff 审查。

文档提案阶段至少应执行适用于文档的检查和 `git diff --check`。代码实施阶段先运行聚焦检查，再按仓库风险和规则运行完整门禁。不能把 Git Hook 可能执行的检查当作自己已经执行过。

### PR 或交付报告必须说明

- 新增、合并、部分保留、拒绝、归档或删除了多少提案和 TODO；
- 调查了哪些领域；
- 有意排除了哪些领域及原因；
- 每个实施项减少了哪些 API、状态、分支、包或维护产物；
- 放弃了哪些能力，是否有行为或兼容变化；
- 执行了哪些检查，结果如何；
- 哪些风险仍需人工或后续环境验证。

对于决策记录合并，还须指出旧所有者和当前所有者、完全取代的证据，以及删除旧记录为何安全。若“新增后又删除”扫描没有找到合格记录，也应报告这一结果和被保留的代表性部分取代案例。

调查尚在扩张、候选项仍在变化或审查意见尚未处理完时，使用 Draft PR。只有候选集合、审查响应和验证均稳定后才标记为 Ready。

## 候选项优先级建议

不要只按预计删除行数排序。可综合以下维度：

| 维度 | 高分含义 |
| --- | --- |
| 证据强度 | 已排除生产、动态和外部消费者 |
| 契约缩减 | 明显减少公共 API、协议、Schema 或配置组合 |
| 状态缩减 | 合并重复事实、生命周期或所有权机制 |
| 维护收益 | 可删除实现、专用测试、文档、包和发布责任 |
| 实施独立性 | 能在小范围内独立完成并验证 |
| 行为风险 | 风险越低得分越高 |
| 兼容风险 | 无外部兼容义务得分越高 |
| 可逆性 | 易回退、无数据破坏得分越高 |

推荐优先处理“证据强、契约缩减明显、实施独立、风险低”的候选项，而不是单纯追求最大删除量。大规模删除往往代表产品范围调整，应单独获得授权。

## 可直接交给 Agent 的完整审计提示词

下面的提示词是本文规则的可执行版本。使用时替换尖括号中的项目变量；如果仓库已有更高优先级的 Agent 规则，以仓库规则为准。

```text
请对当前仓库执行一次完整的“删除式精简审计”，寻找死代码、重复状态、推测性能力、过度构建、已添加后又移除的残留、仅由测试或文档消费的表面积，以及可以被标准库或成熟依赖净替换的手写基础设施。

目标不是最大化删除行数，而是以证据为基础，减少不再产生价值的公共 API、状态表示、生命周期机制、配置组合、包边界、兼容层、测试产物和维护责任。

本阶段默认只调查和编写提案，不修改生产代码。除非用户明确要求直接实施，否则在候选项获得确认前停止在审计结果。

一、保护工作区和确认基线

1. 阅读当前目录和父目录适用的 AGENTS.md、CLAUDE.md、贡献指南及其他 Agent 规则。
2. 执行 git status，保护用户已有改动，不覆盖、回滚、格式化或提交任务范围外的文件。
3. 按仓库规则检查远程更新，记录当前分支、远程目标基线和审计范围。
4. 如果工作区改动、分支分叉或远程同步可能覆盖用户工作，停止写入并说明阻塞。

二、建立仓库上下文

1. 阅读 README、产品范围、路线图、发布说明、架构文档、测试规范、安全规范和防御模式说明。
2. 阅读工作区、包管理、编译、构建、打包、发布和 CI 配置，识别真实生产入口。
3. 阅读 ADR、RFC、设计提案、Issue 和历史迁移文档，区分当前架构意图与已经过时的历史判断。
4. 确定项目兼容阶段：未发布、快速迭代、稳定公共 API、持久化数据兼容、插件生态或外部协议。
5. 建立受保护设计清单，包括明确要求保留的多平台实现、主备后端、协议适配器、兼容读取器、安全隔离和回滚能力。
6. 不要把受保护的并行实现直接判定为重复；可以调查其内部无人使用的方法或钩子。

三、发现并划分语料库

不要假定生产代码一定在 src 或 packages。根据入口、构建、路由、工作区、插件、依赖注入和动态加载配置识别：

- 生产语料库：进入构建、打包、部署或运行加载路径的代码、配置、资源、迁移和脚本；
- 非生产语料库：测试、文档、ADR/RFC、快照、Fixture、Golden、注释和开发工具；
- 用途不明确语料库：示例、脚本、实验目录、调试页和 Smoke Test，阅读用途后再分类。

四、广度调查

覆盖与当前仓库有关的领域：

- 领域与应用服务；
- 状态、缓存、持久化、迁移、恢复和重放；
- UI、路由、交互状态和不可达入口；
- IPC、HTTP、消息、Worker、子进程和原生桥接；
- 外部服务、供应商和平台适配器；
- 工具执行、任务所有权、取消、临时文件和输出缓存；
- 包、模块、公共导出、支持代码和重复启动胶水；
- 配置、功能开关、环境变量、插件和动态注册；
- 测试、Mock、Fixture、Golden、快照和生成产物；
- 构建、发布、废弃 CLI、迁移脚本和平台分支；
- 文档和决策记录。

如果用户要求广度或多个候选项，可以把互不依赖的领域交给多个 Agent 并行调查；每个 Agent 必须提交调用证据，不得只提交猜测。没有子 Agent 时由当前 Agent 顺序完成同等范围。不要找到第一个候选项就停止。

优先检查生产代码变化量大、长期高频修改、重复生命周期和防御机制多、历史上反复新增删除的区域，而不只检查浅层未使用符号。

五、强候选项标准

重点寻找：

1. 没有生产消费者的公共方法、导出、事件、配置项、注册通知、帮助函数、包、进程、持久化事件、协议字段或测试产物。
2. 只有测试、文档、示例或快照消费，且行为不承担真实契约的表面积。
3. 表达同一事实的两套状态、事件、缓存、摘要、默认值、错误分类或持久化记录。
4. 所有实现都必须提供、但生产调用方从未使用的接口方法和 Hook。
5. 只为测试、演示、支持或重复启动胶水存在，却增加发布和依赖成本的独立包。
6. 没有当前产品所有者的推测性能力，如未使用的多实例、后台任务名册、热注册、复杂恢复、中途转向或大量策略组合。
7. 只用于保护废弃 API 的不变量、回滚、补偿、专用错误、测试、Fixture、Golden 和快照。
8. 可以由目标运行时标准能力或健康依赖覆盖，并能获得净删除的手写基础设施。
9. 已被新实现完全取代，但仍残留在生产、配置、Schema、兼容层、测试或文档中的旧路径。
10. 行为可以略微调整为更合理、更容易解释的语义，并能显著减少特殊分支；必须明确行为差异。

六、搜索和证据要求

对每个符号或行为：

1. 使用 rg 搜索精确符号、事件名、包名、配置键、协议字符串和文件名。
2. 对方法搜索 .name(、name(、可选链、绑定、解构和接口实现。
3. 检查导出、再导出、桶文件、路由表、注册表、Schema、菜单、命令、模板和动态导入。
4. 检查 IPC Channel、HTTP 路径、数据库字段、持久化事件、消息 Topic、环境变量和构建入口。
5. 阅读每个可信调用点，解释真实用途。
6. 将消费者分为生产、非生产和用途不明确三类。
7. 对“没有生产消费者”的结论写明搜索范围、搜索词和排除动态消费的方法。
8. 可使用 knip、编译器、IDE、覆盖率和依赖图辅助，但不能用工具输出代替调用点理解。
9. 使用 git log、git log -S、git log -G 和 git blame 理解引入原因，但不以提交标题和日期代替当前证据。
10. 注意仓库外消费者；公共 SDK、插件、协议、持久化数据和脚本入口不能仅凭仓库内零引用删除。

七、信任和生命周期审计

对防御性复制、冻结、校验、序列化、回调捕获和异常隔离，说明值的来源、信任程度、当前所有者、下一所有者以及是否跨进程、网络、持久化或原生边界。

同进程强类型只读交接中的敌意对象测试可能代表推测性契约；解析器、配置、队列、外部 JSON、持久化、Worker、子进程和网络边界则应拥有并验证数据。身份认证、授权、路径、反序列化、签名和密钥安全不能按调用次数删除。

对复杂异步代码画所有权图，把哨兵、状态、readiness/settlement Promise、取消、超时、disposer、Worker、进程和队列映射到独立所有者或状态迁移。多个机制镜像同一存活或完成事实时考虑统一控制器；同步发布回滚、回调隔离、首终态竞争、进程所有权和 dispose-to-quiescence 等不同语义应保持独立。

八、依赖替换审计

如果标准库或依赖可能替代手写实现：

1. 读完手写实现，列出依赖覆盖和未覆盖的准确语义。
2. 检查维护、采用度、传递依赖、许可证、安全、平台、包体积、冷启动、Native 和离线安装成本。
3. 检查已有架构决策，不能只用“成熟依赖优先”推翻被保护的实现。
4. 计算删除实现、专用测试和文档后，扣除适配胶水、配置和治理成本的净收益。
5. 优先使用项目最低运行时版本已经提供的标准能力。
6. 如果包装器只是搬移复杂度，拒绝该候选项。

九、拒绝和升级规则

出现以下情况时拒绝、降级或改变候选项性质：

- 有生产调用者：标记为需要产品决策；
- 有公共 API、外部消费者或持久化兼容：标记为需要迁移/弃用计划；
- 有仍成立的架构记录或事故防御依据：保留，除非新证据足以推翻；
- 只减少文件或行数，不减少契约和行为：拒绝；
- 引发大量无关改动：缩小范围；
- 问题真实但很小：直接修复或记录稳定标签 TODO；
- 动态使用无法排除：证据不足；
- 依赖成本或安全风险超过收益：拒绝；
- 删除会破坏受保护的多后端、多平台、容灾或安全边界：拒绝或请求产品授权。

十、候选项输出

每个候选项必须包含：

1. 以动作开头的名称；
2. 结论：推荐清理、需要产品决策、需要迁移/弃用计划、保留、证据不足、局部 TODO 或拒绝；
3. 当前表面积及准确文件、符号、事件、配置、协议或包；
4. 生产消费者及用途；没有则写明搜索证据；
5. 非生产消费者；
6. 动态和仓库外消费风险；
7. 当前架构理由和历史来源；
8. 具体删除、合并、降级、内联、重新归属或替换动作；
9. 会同步删除或更新的测试、文档、Schema、快照、Fixture、Golden 和生成文件；
10. 继续保留它的最强理由；
11. 将放弃的能力和行为差异；
12. 替代方案；
13. 公共 API、兼容、数据、安全、性能、发布和未来需求风险；
14. 预计减少的 API、状态、分支、包、依赖、测试、文档和净代码行；
15. 验收标准和验证命令；
16. 实施范围与明确排除项。

按证据强度、契约缩减、维护收益、实施独立性和风险排序。只输出证据最充分的候选项；不要为了凑数量制造薄弱提案。如果没有可靠候选项，明确报告没有发现。

十一、提案文档

遵循仓库已有 ADR/RFC/提案路径。若没有约定，使用 docs/simplification/proposed/yyyy-mm-dd-topic.md。每个持久化提案包含：问题、证据、提案、为什么不保留、我们放弃什么、替代方案、验收标准、风险与缓解、实施范围。

小型局部问题使用有稳定标签且可执行的 TODO/FIXME/XXX；不要把需要产品或架构判断的问题降级成注释。

十二、最终审计报告

总结：

- 新增、合并、保留、拒绝或降级了多少候选项；
- 调查领域和有意排除领域；
- 受保护设计清单；
- 最高优先级候选项及排序依据；
- 需要用户作出的产品或兼容决策；
- 执行过的搜索、文档检查和其他验证；
- 仍然存在的证据缺口。

在用户选择候选项前，不进入实施阶段。
```

## 可直接交给 Agent 的实施提示词

```text
请实施已经批准的精简提案：<提案路径或候选项名称>。

只处理该提案，不进行相邻模块的机会主义重构。仓库规则和用户明确指令优先于本提示词。

一、实施前复核

1. 阅读适用的 Agent 规则、提案全文、相关架构决策和受影响模块文档。
2. 检查 git status 和远程基线，保护用户已有改动。
3. 重新搜索生产、非生产、动态和外部消费者，确认提案前提仍成立。
4. 确认兼容阶段、修改范围、明确排除项和回退方法。
5. 如果发现生产调用者、公共外部消费者、持久化兼容义务或不同生命周期语义，停止或缩小范围，并报告新证据。

二、实施要求

1. 删除、合并、降级、内联、重新归属或替换提案指定的生产表面积。
2. 同步删除不再成立的公共类型、导出、注册、配置、Schema、协议字段和兼容包装。
3. 不要仅为旧测试继续通过而保留无人使用的兼容层。
4. 删除只保护废弃行为的测试、Mock、Fixture、Golden、快照和生成预期文件。
5. 保留仍然负载真实行为的接口、状态、防御和生命周期机制。
6. 必要时把测试改为通过真实公共入口验证保留行为，避免穿透私有状态。
7. 更新 README、架构文档、API 文档、JSDoc、Schema、事件表、迁移说明、目录索引和生成文件。
8. 若精简使旧决策记录完全失效，按记录治理规则迁移独有理由、修复链接并原子处理配套文件；部分失效则保留并交叉链接。
9. 不修改、格式化、暂存或提交任务范围外的文件。

三、验证要求

1. 搜索被删除的精确符号、文件名、配置键、事件名、协议字符串和旧文档链接。
2. 执行受影响模块的聚焦测试。
3. 从当前仓库配置中发现并执行适用的类型检查、lint、单元/契约/集成/E2E、架构、构建、打包、迁移和文档同步门禁。
4. 涉及公共 API、协议或持久化时验证兼容或明确验证破坏性变更。
5. 执行 git diff --check，检查完整 git diff 和 git diff --stat。
6. 确认净结果确实减少了公共契约、状态、分支、包、依赖或维护产物，而不是把复杂度转移到新包装器。

四、最终报告

报告：

- 删除、合并或保留了什么；
- 原提案是否因新证据缩小；
- 减少了哪些 API、状态、分支、包、依赖、测试和文档；
- 净代码变化；
- 行为和兼容性变化；
- 执行的验证及结果；
- 未执行的验证及原因；
- 剩余风险和回退方式。
```

## 可直接交给审查 Agent 的复核提示词

```text
请以反对者视角审查本次精简改动，不继续扩大实现范围。

重点验证：

1. “没有生产消费者”的搜索是否遗漏动态导入、注册表、路由、配置、模板、IPC、协议、持久化或仓库外消费者。
2. 被删除的两套状态是否真的表达同一事实，还是具有不同所有者、信任边界、生命周期或恢复责任。
3. 被删除的防御是否位于真实安全边界。
4. 被删除的测试是否只保护废弃行为，保留行为是否仍有真实路径覆盖。
5. 依赖替换是否获得净简化，还是把复杂度搬到包装器、配置或供应链。
6. 公共 API、插件、协议、数据库和持久化格式是否需要弃用或迁移。
7. 文档、Schema、快照、Fixture、Golden、生成文件和决策记录是否同步。
8. 改动是否越过提案范围或夹带机会主义重构。
9. git diff 是否显示真正缩小契约、状态或维护责任。
10. 测试、类型检查、lint、构建、打包和残余引用搜索是否与风险相称。

对每个问题给出文件和调用证据。将发现分类为：必须修复、需要产品决策、证据不足或可以接受。不要因为删除行数很多就默认改动正确。
```

## 最终判断标准

一项精简只有同时满足以下条件才算完成：

- 删除前提经过当前代码和真实调用路径验证；
- 生产功能、产品决策和普通清理被明确区分；
- 放弃的能力与兼容影响被公开记录；
- 相关实现、接口、配置、测试、文档和生成产物被一致处理；
- 安全、数据和生命周期边界没有因追求简短而被破坏；
- 验证与改动风险相称；
- 最终结果减少的是系统必须理解和维护的事实，而不仅是文本行数。
